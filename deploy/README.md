# Production host files

These files turn a fresh Fedora 45 VPS into the Kasten mail host. `tang/` sets up automatic disk unlock on a second host. The full walk-through, with the provider steps, is [the install guide](../docs/install-vps.md). This page is the reference.

## Order of use

This list covers the host only. The install guide adds DNS, SES, the users, the web app and the security check around it. Run every command on the VPS as root. The commands work from any directory.

1. Join the VPS to Tailscale, or know the public address you connect from. Check that `getenforce` prints `Enforcing`: install.sh and the containers need SELinux. If it prints `Permissive`, set `SELINUX=enforcing` in `/etc/selinux/config` and reboot. If it prints `Disabled`, label the files in permissive mode first, as in [install section 3](../docs/install-vps.md#3-install-fedora-45). That relabel has not yet been tried on a provider image.
2. Copy this directory to the VPS, for example with `scp -r deploy root@<vps>:`.
3. Run `deploy/host/install.sh --mail-api-host mail.example.com` as root. Use the `mailApiHostname` from your `kasten.json`. install.sh writes `STALWART_PUBLIC_URL=https://mail.example.com` into `/opt/kasten/.env`. On a terminal it asks twice for a new recovery passphrase of at least 20 characters. An agent can pass the passphrase on standard input instead: it pipes the passphrase over SSH from a 0600 file on its own computer. A file on the VPS's disk keeps its blocks after deletion, so if the agent needs `--passphrase-file FILE`, FILE goes under `/run`, in RAM. Add `--admin-ips "<your address>"` if you are not on the tailnet. Save the passphrase in your password manager. See [install.sh](#installsh) for every option.
4. On your computer, build both images for `linux/amd64` with Docker, from the repository root, then load them into the kasten user's Podman on the VPS:

   ```sh
   docker build --platform linux/amd64 -t kasten-server:<version> server/
   docker build --platform linux/amd64 -f cli/Dockerfile -t kasten-cli:<version> .
   docker save kasten-server:<version> kasten-cli:<version> | ssh root@<vps> kasten-podman load
   ```

   Podman names them `localhost/kasten-server:<version>` and `localhost/kasten-cli:<version>`. Every container starts with `--pull=never`, so the VPS never pulls an image. The VPS has no Docker: build the images on your computer.

5. Set `KASTEN_VERSION=<version>` in `/opt/kasten/.env`.
6. Run `kasten-mail-run init`. Put the `volumeId` it prints into `/opt/kasten/.env` as `KASTEN_VOLUME_ID`.
7. Put `kasten.json` and the files it names into `/var/lib/kasten/cli/`. Leave out the admin API key file: bootstrap writes it. Set `admin.apiUrl` to `http://127.0.0.1:8080` and `admin.allowedIps` to `["127.0.0.1", "::1"]`. Then give every file there to the kasten user, without group or other access: `chown -R kasten:kasten /var/lib/kasten/cli && chmod -R go= /var/lib/kasten/cli`. `kasten-cli` refuses to run otherwise, and prints this command.
8. Run `kasten-bootstrap`. It starts Stalwart in recovery mode in a container without any network, runs `kasten setup --bootstrap` in that container's network namespace, and stops recovery mode. The admin API key is then in the file that `admin.apiKeyFile` names, for example `/var/lib/kasten/cli/admin-api-key`. Save it in your password manager: a [restore after host loss](../docs/operations.md#restore-after-host-loss) needs it. See [First boot without downloads](#first-boot-without-downloads). If the volume is locked, for example after a reboot, `kasten-bootstrap` stops and names the unlock command, `kasten-unlock-passphrase`. Until the first boot is done, that command mounts the volume and does not start Kasten.

   With `http.mode` set to `production`, the bootstrap does not create the ACME provider (`x:AcmeProvider`) or the certificate settings, and lists them as `deferred`. Stalwart registers the ACME account when it creates the provider, and refuses the provider when the directory is unreachable ([Stalwart notes, section 11](../docs/stalwart-v1.0.1.md#11-production-tls-with-acme-tls-alpn-01)). The first normal setup in step 9 creates them. A unit test runs both steps of `kasten.example.json` against a stand-in server; `test/run.sh` uses the dev-mode listener ([Limits](#limits)).

9. Run `systemctl start kasten.service`, then `kasten-cli setup --config /etc/kasten/kasten.json`. The start returns once the mail container is healthy: Podman runs its first health check 30 seconds after the start. In production mode, this run also creates the ACME provider, which contacts the certificate authority. If setup prints `Restart Stalwart to apply`, run `systemctl restart kasten.service`. Run setup a second time: it reports `0 changed`.
10. Set up Tang as in [tang/README.md](tang/README.md), then run `kasten-bind-tang <url> <thumbprint>`. It asks for the recovery passphrase, or reads it from standard input.
11. Set up backups, as described below. Run one backup and one restore before real mail.
12. Set up the daily check, as described below, after the user has created their key in the app.
13. Prove the off-host delivery observer on the pilot domain, then verify its production account after the MX switch. Co-located probes remain optional.
14. Reboot. Check that the disk unlocks and that mail starts without you.

Of Kasten's own timers, the installer enables only the backup timer. Set up the [off-host observers](observer/README.md) separately. The mail-host check and probe unit files are installed for operators who need them.

## install.sh

`deploy/host/install.sh --help` prints this list. install.sh keeps the options in `/etc/kasten/host.env`, so a later run without them keeps the earlier values.

| Option                   | Does                                                                                                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--admin-ips "ADDR ..."` | Also allows SSH from these IPv4 or IPv6 addresses or networks, on any interface. SSH over `tailscale0` is always allowed                                                         |
| `--data-size SIZE`       | The size of the volume file, for example `24G`. Used only when install.sh creates the volume. Default `auto`: the free space on the root file system at install time minus 6 GiB |
| `--mail-api-host NAME`   | Sets `STALWART_PUBLIC_URL=https://NAME` in `/opt/kasten/.env`. Without it, install.sh keeps the URL there, asks on a terminal, or stops                                          |
| `--passphrase-file FILE` | Reads the new recovery passphrase from the first line of FILE. Keep FILE under `/run`, in RAM                                                                                    |
| `--skip STEP`            | Skips a step. Repeat it for more steps                                                                                                                                           |

install.sh runs only on Fedora: `ID=fedora` in `/etc/os-release`, with a `VERSION_ID` in its `SUPPORTED` list, now 44 and 45, and with systemd running. A release joins that list only after the local tests pass on it. Fedora 45 passed `deploy/test/run.sh all` and the Lima stage `f45`. Fedora 44 passed the Lima stage `upgrade`, which installs Kasten on Fedora 44 and serves, checks and backs up mail there before it upgrades to 45. See [The acceptance test](#the-acceptance-test). install.sh also stops unless SELinux enforces the targeted policy with MCS (`/sys/fs/selinux/mls` is `1`): the containers' MCS levels keep the mail server away from the CLI's credentials.

The file `/etc/kasten/test-without-selinux` turns the SELinux check off, in install.sh and in kasten-podman. Both then print a loud warning and log `event=selinux-check result=skipped`. Only the local container test (`deploy/test/run.sh`) creates the file, because its container cannot enforce SELinux. Never create it on a real host: without SELinux, the mail server could read the CLI's credentials.

The steps run in this order:

| Step       | Does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages` | Writes `/etc/dnf/repos.override.d/50-kasten-https.repo` before the first download, so that dnf5 uses only HTTPS mirrors. Installs `podman crun conmon passt nftables cryptsetup clevis clevis-luks dnf5-plugin-automatic dnf5-plugins zram-generator sqlite e2fsprogs jq curl policycoreutils util-linux diffutils` without weak dependencies. Writes `/etc/dnf/automatic.conf`, enables `dnf5-automatic.timer` and masks `dnf-makecache.timer`                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `journald` | Keeps the journal in RAM, with no forwarding to syslog. Stops if a syslog daemon (`rsyslog` or `syslog-ng`) is installed, because it would write the logs to the unencrypted disk. Masks `auditd.service`, which would write the audit log there; the kernel's audit messages still reach the journal in RAM. Turns off stored core dumps                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `swap`     | Turns off disk swap, comments out every swap row in `/etc/fstab`, including rows that end after the type, and stops if one stays active. Masks every `.swap` unit whose device (`systemctl show -p What`, with links resolved) is not a `/dev/zram*` device, because systemd also finds a GPT swap partition without fstab. The zram device's units for its other names, such as `dev-disk-by\x2dlabel-zram0.swap`, stay unmasked. Writes `/etc/systemd/zram-generator.conf`. If that file changed or no zram swap is active, it stops `systemd-zram-setup@zram0.service`, resets `/dev/zram0` once udev has settled, and starts `dev-zram0.swap`: a restart of the setup unit can lose a race with udev and leave no swap. If the device stays busy after 10 tries, it stops with `/dev/zram0 stays busy. Reboot, then run install.sh again.` Stops unless zram swap is active |
| `fstrim`   | Enables `fstrim.timer`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `user`     | Creates the user `kasten`: uid and gid 2600, home `/home/kasten`, shell `/usr/sbin/nologin`, password locked. Checks that `/etc/subuid` and `/etc/subgid` give it the same range of at least 65536 IDs, and writes `KASTEN_MAIL_UID` into `/etc/kasten/host.env`. Turns on linger, so that `user@2600.service` starts at boot, and starts it. Masks `systemd-oomd.service` and `systemd-oomd.socket`. Installs `conf/sysctl.conf` and `conf/containers.conf`, and has the `kasten` user write `conf/storage.conf` into its own home: root never writes into a directory of `kasten`'s, where a link could lead it to any file. Stops if uid or gid 2600 belongs to someone else, if the subordinate range changed since the last run, if another file sets `net.ipv4.ip_unprivileged_port_start`, or unless `kasten-podman info` reports rootless Podman with a transient store |
| `volume`   | Creates, unlocks and mounts the LUKS2 volume if it does not exist, with `data/`, `secrets/`, `cli/` and `cli/state/`, owned as in [What lives where](#what-lives-where). The `kasten` user creates `cli/state/`, inside its own `cli/`. Makes the empty mount point immutable. On btrfs, turns off copy-on-write for the volume file. Labels the new file system for SELinux once (`restorecon`). A run that stops while it creates the volume, also through Ctrl-C, a dropped SSH session or SIGTERM, removes the incomplete volume file                                                                                                                                                                                                                                                                                                                                       |
| `units`    | Installs the helpers, `/usr/local/lib/kasten/podman.sh`, the units and `/opt/kasten/.env`. Enables `kasten-unlock.service` and `kasten.service`, also after [the Fedora release upgrade](../docs/operations.md#the-fedora-release-upgrade), which disables them. Of Kasten's timers, it enables and starts only `kasten-backup.timer`. It does not enable check/probe timers; preserve existing operator-owned timer state                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `firewall` | Fills the admin addresses into `nftables.conf`, writes it as `/etc/sysconfig/nftables.conf`, installs the drop-in for `nftables.service` and enables the unit. Loads the rules with `systemctl reload-or-restart nftables.service`: the drop-in's reload loads the file, which replaces only the `inet kasten` table, and a reload does not count against the unit's start limit (five starts in 10 s), which quick runs of install.sh would reach. An inactive unit is started. Disables and masks `firewalld.service` if it is installed. Stops if neither `tailscale0` nor an admin address would allow SSH, or if the firewall would cut the current SSH session                                                                                                                                                                                                            |

## What lives where

| Path                                           | Holds                                                                                                                                                                                                                                           |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/var/lib/kasten.luks`                         | The encrypted volume: a sparse LUKS2 file on the root file system                                                                                                                                                                               |
| `/var/lib/kasten`                              | Its mount point. Immutable while unmounted, so nothing can write there                                                                                                                                                                          |
| `/var/lib/kasten/data`                         | The server's data volume, owned by `KASTEN_MAIL_UID`, at the mail containers' SELinux level. The mail container sees it as `/var/lib/kasten`                                                                                                    |
| `/var/lib/kasten/secrets`                      | Root-only host secrets, for example `backup.env`. It is never mounted into a container                                                                                                                                                          |
| `/var/lib/kasten/cli`                          | Owned by `kasten`, at the CLI's SELinux level. The CLI container sees it read-only as `/etc/kasten`: `kasten.json`, the admin API key and the other credentials                                                                                 |
| `/var/lib/kasten/cli/state`                    | Owned by `kasten`, at the CLI's SELinux level. The CLI container sees it writable as `/etc/kasten/state`: the pinned key sets, reader credentials, check state, setup's due restart (`setup-restart.json`) and due lock (`setup-lock-due.json`) |
| `/var/lib/kasten/.kasten-bootstrap-incomplete` | Exists only while a first boot has not finished. See [First boot without downloads](#first-boot-without-downloads)                                                                                                                              |
| `/opt/kasten/.env`                             | `KASTEN_VERSION`, `KASTEN_VOLUME_ID` and `STALWART_PUBLIC_URL`. Not secret. Every line reaches `kasten-mail` and each `kasten-mail-run` container                                                                                               |
| `/etc/kasten/host.env`                         | The settings from `host/host.env`, with the `KASTEN_MAIL_UID` that install.sh sets                                                                                                                                                              |
| `/usr/local/lib/kasten/podman.sh`              | The containers' Podman arguments, which kasten.service and the helpers use                                                                                                                                                                      |
| `/home/kasten/.local/share/containers/storage` | Podman's images, on the root disk. They survive a reboot                                                                                                                                                                                        |
| `/run/user/2600/containers`                    | Podman's database and the state of every container and exec (the transient store), in RAM                                                                                                                                                       |

The kasten user runs every container, with rootless Podman. Container root is kasten itself, and container uid N runs as kasten's Nth subordinate ID. So the server's uid 2525 owns its files on the host as `KASTEN_MAIL_UID`, the first subordinate ID plus 2524: for example 526812, when kasten's range starts at 524288.

Without the mount, `/var/lib/kasten/data` does not exist, and Podman refuses to start the mail container. The server also refuses a volume without its marker, or with a different volume id.

## Nothing on the unencrypted disk

Every container has a read-only root file system, and its logs go to journald, which keeps them in RAM. Podman writes no log file for them. Its only log file, the health check's `healthcheck.log`, is under `/run/user/2600`, in RAM. Stalwart logs envelope addresses at info level, so these logs must not reach the disk.

| Container                                                       | Writable path                                          | Where it lives                       |
| --------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------ |
| `kasten-mail`, `kasten-recovery`, a `kasten-mail-run` container | `/var/lib/kasten`                                      | The encrypted volume                 |
| `kasten-mail`, `kasten-recovery`, a `kasten-mail-run` container | `/run/kasten` (tmpfs, 4 MiB): Unbound's working files  | RAM                                  |
| A `kasten-cli` container                                        | `/etc/kasten/state`                                    | The encrypted volume                 |
| The bootstrap CLI                                               | `/etc/kasten`, to write the admin API key              | The encrypted volume                 |
| A `kasten-cli` container, the bootstrap CLI                     | `/tmp` (tmpfs, 16 MiB)                                 | RAM                                  |
| Every container                                                 | `/dev`, `/dev/shm`, `/dev/pts`, `/dev/mqueue`, `/proc` | RAM and the kernel (Podman defaults) |

With host networking, a rootless container also sees the host's `/sys` and the kernel's pseudo-filesystems below it, such as cgroup2 and selinuxfs, as writable mounts. They are kernel interfaces, not files on the disk.

Podman keeps its database and the state of every container and exec in `/run/user/2600/containers`, in RAM: the kasten user's `storage.conf` sets `transient_store = true`. That state includes each exec's environment, such as the backup settings, and each run's arguments, such as an address in a `kasten-cli` command. Only the images stay on the disk, in `/home/kasten/.local/share/containers/storage`.

A core dump holds the crashed process's memory. systemd-coredump would store it in `/var/lib/systemd/coredump` on the disk, so install.sh tells it to store none.

The Fedora Cloud image keeps a persistent journal in `/var/log/journal`, and auditd writes `/var/log/audit/audit.log`. install.sh switches journald to RAM and masks auditd, but leaves the files from before that point. They hold only the logs of the first boot and of the install. Delete them if you want none. Otherwise record the journal files right after install.sh, as in [install section 5](../docs/install-vps.md#5-run-the-host-install-script), step 6: the acceptance checks then show that none of them changed. `/var/log/dnf5.log` stays on the disk; it holds package names only.

`test/run.sh` reads the mail container's mount table and checks that every writable mount is the encrypted volume, RAM or a kernel pseudo-filesystem. It also checks that Podman's diff of the mail container shows only `C /etc`, that Podman's storage holds no `*.log` file, and that `kasten-residue-check` finds the envelope address of the test mail in no file on any disk file system. These checks passed in the `run.sh` run that [The acceptance test](#the-acceptance-test) describes, in a container without SELinux.

## First boot without downloads

Stalwart's first start in recovery mode inserts an enabled web admin UI and tries to download it from GitHub. Its first normal start would download ASN/GeoIP data. The spam rules also bring four remote lists (`x:HttpLookup`: OpenPhish, PhishTank, disposable and free mail domains), which Stalwart would fetch at their first lookup. `kasten-bootstrap` prevents all three:

1. It copies the recovery login to `/var/lib/kasten/cli/recovery-admin`, owned by `kasten`, mode 0600, for this run. The CLI container runs as kasten, which cannot read the server's original.
2. It starts `kasten-recovery`, the mail server's container in recovery mode, with `--network=none`, and waits up to 300 seconds until it is healthy.
3. The bootstrap CLI container runs `kasten setup --config /etc/kasten/kasten.json --bootstrap --recovery-admin-file /etc/kasten/recovery-admin --url http://127.0.0.1:8080` with `--network=container:kasten-recovery`, so it shares the recovery container's loopback and nothing else. It sees `/var/lib/kasten/cli` writable as `/etc/kasten`. Setup creates the admin API key. It stores every `x:Application`, `x:Asn` and the four remote lists as disabled.
4. It removes the recovery container and deletes the copy of the recovery login. This cleanup also runs when Ctrl-C, a dropped SSH session or SIGTERM ends `kasten-bootstrap`.

In recovery mode, the web UI download fails, because there is no network. On the first normal start, nothing is enabled that would download. That start imports the pinned spam rules from the volume, and the import keeps each list's stored `enable`. The first normal `kasten setup` then sets every `x:HttpLookup` to disabled again.

A normal start before the bootstrap would download. So `kasten.service` and `kasten-unlock-passphrase` start Stalwart only when both of these hold:

| Condition                                                     | Why                                                                                                          |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `/var/lib/kasten/data/stalwart/stalwart.sqlite` exists        | Stalwart creates it at its first start, which is recovery mode under `kasten-bootstrap`. A restore brings it |
| `/var/lib/kasten/.kasten-bootstrap-incomplete` does not exist | `kasten-bootstrap` creates it before a first boot and deletes it when setup has finished                     |

Until then, `systemctl start kasten.service` fails with an assertion, and `kasten-unlock-passphrase` mounts the volume and names the next step. A bootstrap that stops part-way keeps the second file, so a half-configured database never starts with a network. Run `kasten-bootstrap` again. A host that replaces another one gets its database from a restore instead, as in [Moving to another host](../docs/operations.md#moving-to-another-host) or [Restore after host loss](../docs/operations.md#restore-after-host-loss).

## Backups

`/var/lib/kasten/secrets/backup.env` (root, mode 0600) holds these lines:

| Line                      | Value                                                                                                |
| ------------------------- | ---------------------------------------------------------------------------------------------------- |
| `RESTIC_REPOSITORY=`      | For example `s3:https://s3.eu-central-003.backblazeb2.com/<bucket>/kasten`                           |
| `RESTIC_PASSWORD_FILE=`   | `/var/lib/kasten/secrets/restic-password`, a path inside the container                               |
| `KASTEN_BACKUP_ENV_FILE=` | `/var/lib/kasten/secrets/restic-backend.env`, a path inside the container, with the bucket key lines |
| `KASTEN_PUSH_URL=`        | Optional: the Kuma push URL for the backup monitor, in double quotes, because it holds `&`           |

On the host, the two files are `/var/lib/kasten/data/secrets/restic-password` and `/var/lib/kasten/data/secrets/restic-backend.env`. Write each one as `KASTEN_MAIL_UID`, the server's user on the host, which gives it that owner and mode 0600: `. /etc/kasten/host.env; setpriv --reuid="$KASTEN_MAIL_UID" --regid="$KASTEN_MAIL_UID" --clear-groups sh -c 'umask 077 && cat >/var/lib/kasten/data/secrets/<file>'`, with the content on standard input. Root itself never writes into `data/`, as in [docs/operations.md](../docs/operations.md#how-to-run-the-commands-on-this-page). `restic-password` holds the repository password on one line. `restic-backend.env` holds `NAME=value` lines: `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` for B2's S3 API, or `B2_ACCOUNT_ID` and `B2_ACCOUNT_KEY` for a `b2:` repository. Save the repository password in your password manager too: without it, nobody can read the backups. On Backblaze B2, a delete through the S3 API only hides a file, so an `s3:` repository there needs a lifecycle rule on the bucket, or pruned snapshots keep their storage and cost. See [Bucket key choices](../docs/operations.md#bucket-key-choices).

While `kasten.service` runs, create the repository once and start the first backup. The timer runs the later ones:

```sh
set -a; . /var/lib/kasten/secrets/backup.env; set +a
kasten-mail-exec backup-init
systemctl start kasten-backup.service
```

Of the lines in `backup.env`, `kasten-mail-exec` and `kasten-mail-run` pass only `RESTIC_REPOSITORY`, `RESTIC_PASSWORD_FILE` and `KASTEN_BACKUP_ENV_FILE` into the container. Keep credentials out of `RESTIC_REPOSITORY`, and put them in the file that `KASTEN_BACKUP_ENV_FILE` names: `kasten-podman` passes the three values in a process's arguments, which every host user can read ([security model](../docs/security.md#container-isolation-on-the-host)).

Restore with the mail service stopped:

```sh
systemctl stop kasten.service
set -a; . /var/lib/kasten/secrets/backup.env; set +a
kasten-mail-run restore latest
systemctl start kasten.service
```

Instead of `latest`, `restore` takes a snapshot id. It keeps the old database as `stalwart.sqlite.before-restore-<UTC time>`, with its `-wal` and `-shm` files. Once the restored server works, delete them: `rm /var/lib/kasten/data/stalwart/stalwart.sqlite.before-restore-*`. See [the server's restore steps](../server/README.md#restore).

## The daily check

Run this check from a separate trusted machine. Follow [observer setup](observer/README.md), copy protected lock and reader state after authorized changes, and use the private admin tunnel and public reader URL. Run one aggregate check for the combined monitor status.

After `kasten-cli reader rotate --account <email> --config /etc/kasten/kasten.json`, replace the Mac observer's reader copy with the new reader file. The old reader stops signing in. Pass `--allowed-ip` to `reader create` or `reader rotate` only when every machine that uses the reader reaches the public reader URL from a fixed address: a Mac's address changes with its network, so the limit would lock out its check. A rotate gives the new reader only the `--allowed-ip` values passed to that rotate. See [Reading mail](../docs/agent-setup.md#reading-mail).

`kasten-check.service` runs `kasten-check` without arguments, so it cannot pass `--exceptions`. Put reviewed exceptions in a file in `/var/lib/kasten/cli`, owned by `kasten` like every file there, and name it in `checkExceptionsFile` in `/var/lib/kasten/cli/kasten.json`. The CLI container sees the file read-only under `/etc/kasten`; a relative name refers to that directory. The file has the `--exceptions` format, for example `{"you@example.com": ["<email id>"]}`.

Run the probe on a separate observer host using only the dedicated probe password, state and push URL. Follow [observer setup](observer/README.md). Prove the pilot round trip before switching the observer at MX cutover.

The probe proves the public MX of its own account's domain. | Task                       | Command                                                                                                                                                                |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lock the disk              | `systemctl stop kasten.service kasten-unlock.service`. Before the first start of kasten.service, also `kasten-unlock stop` (see below)                                 |

| Mail server logs           | `journalctl CONTAINER_NAME=kasten-mail`                                                                                                                                |
| Container state            | `kasten-podman ps -a`. A healthy mail container shows `(healthy)`                                                                                                      |
| Loaded images              | `kasten-podman images`                                                                                                                                                 |
| Run a backup now           | `systemctl start kasten-backup.service`                                                                                                                                |
| Run the check now          | `systemctl start kasten-check.service`                                                                                                                                 |
| The check's report         | `journalctl -t kasten-check`                                                                                                                                           |
| Run the probe now          | `systemctl start kasten-probe.service`                                                                                                                                 |
| The probe's report         | `journalctl -t kasten-probe`                                                                                                                                           |

| Reboot due                 | `dnf5 needs-restarting`. `Reboot should not be necessary.` (exit 0) means none is due; otherwise its message names the updates or the error. Not `-C`: that form fails |
| Updates that ran           | `journalctl -u dnf5-automatic.service`, since the last boot. `/var/log/dnf5.log` keeps the package names                                                               |

Lock through systemd, not with `kasten-unlock stop`, so that the units' state stays true. The one exception: install.sh, and `kasten-unlock-passphrase` before the first boot is done, mount the volume without `kasten-unlock.service`. So if `systemctl is-active kasten-unlock.service` prints `inactive` while `/var/lib/kasten` is mounted, the systemd command locks nothing: also run `kasten-unlock stop`.

Each unlock and lock writes one line for monitoring, for example:

```text
event=unlock result=ok method=tang attempts=1 seconds=3 device=/dev/loop0 dio=1
event=unlock result=failed method=tang reason=timeout attempts=5 seconds=21 device=/dev/loop0
event=unlock result=ok method=passphrase device=/dev/loop0
event=unlock result=failed method=tang reason=mount device=/dev/loop0
event=lock result=ok reason=mount
```

An unlock whose mount fails locks the volume again, so the last two lines come together.

When `KASTEN_UNLOCK_PUSH_URL_FILE` names a URL file, a successful unlock also pushes to the configured event monitor, with the message `unlock ok <method> - acknowledge after review`. A failed unlock cannot read a URL file inside the locked volume; it logs `event=monitoring result=failed`. See [observer setup](observer/README.md#unlock-and-tang-access-events-existing-kuma).

## Choices

| Choice                                          | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Host networking, no published ports             | Stalwart sees the clients' real IPv4 and IPv6 addresses without a proxy in front of it, and no port is published, so the host firewall decides alone. Podman adds no firewall rules. `/etc/sysctl.d/50-kasten.conf` lets the unprivileged kasten user bind ports from 25 up; ports below 25, SSH on 22 among them, stay privileged                                                                                                                                                                                                                                                                                                                                                                                                    |
| Rootless Podman from Fedora                     | No daemon, and no container runs as the host's root: container root is the unprivileged kasten user. Podman, crun and conmon come from Fedora's own repositories, with no third-party repository or key. Their fixes arrive with all Fedora updates, which dnf5-automatic applies every morning: security and bug fixes, and also new upstream versions of Podman, crun, systemd and the kernel. A behaviour change in one of them therefore lands unattended; the daily check and probe catch its effect, not its cause. dnf5-automatic updates only the host's packages: the packages inside the images change only when you rebuild them, as in [Image and dependency updates](../docs/operations.md#image-and-dependency-updates) |
| One container definition, run by kasten.service | `podman.sh` holds the containers' arguments once. kasten.service runs `kasten-mail-service`, which starts and stops the mail container through `kasten-podman`, and `kasten-mail-run`, `kasten-cli` and `kasten-bootstrap` use the same argument lists. No Quadlet unit, which would be a second definition of the mail container. No call from the system manager into the kasten user's manager: such a call starts a transient unit, which systemd refuses while a shutdown is queued, so the stop at a reboot could not remove the mail container before the lock                                                                                                                                                                 |
| setpriv, not runuser                            | `kasten-podman` runs Podman as kasten through `setpriv`, with a clean environment (`env -i`): the kasten user's `HOME`, `XDG_RUNTIME_DIR` and session bus, `TERM`, and only the three backup settings. setpriv changes the user directly; runuser would open a PAM session                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Fixed MCS levels                                | Rootless Podman maps container root to kasten, which owns the CLI's credentials, so file ownership alone cannot keep the mail server away from them. SELinux does: the mail containers run at `s0:c525,c526`, the CLI containers at `s0:c600,c601`, and `:Z` labels each bind-mounted directory with its class's level. With Podman's random levels, every one-shot container would relabel the data directory for itself and cut the running server off its own data. So install.sh refuses to run, and kasten-podman refuses to create a container, unless SELinux is enforcing                                                                                                                                                     |
| Transient store                                 | Podman's database and the state of every container and exec stay in `/run/user/2600/containers`, in RAM. That state holds the backup settings in an exec's environment and the arguments of each CLI run. Only the images stay on the root disk, and they survive a reboot. Every Kasten container is removed when it stops, so none needs its state after a reboot                                                                                                                                                                                                                                                                                                                                                                   |
| No `clevis-systemd`                             | It unlocks `/etc/crypttab` devices through an ask-password agent. `kasten-unlock.service` calls Clevis itself, with a time limit and a log line                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Volume mounted by kasten-unlock                 | A `.mount` unit would wait for a udev device unit. One script that attaches, unlocks and mounts can be tested, and `AssertPathIsMountPoint=` stops kasten.service when the mount is missing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| No disk swap; logs in RAM                       | Swapped memory and journal files would put decrypted mail, metadata and credentials on the unencrypted root disk. Core dumps would too: systemd-coredump stores none                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Read-only containers, journald logs             | A container's writable layer and Podman's `k8s-file` log files would put data outside the encrypted volume. Every container's root file system is read-only. podman.sh sets the journald log driver on every container, and `/etc/containers/containers.conf.d/50-kasten.conf` makes it the default for any other container                                                                                                                                                                                                                                                                                                                                                                                                           |
| Offline first boot                              | Kasten makes no runtime downloads. Only a container without a network can stop Stalwart's first recovery start from fetching its web UI                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| HTTPS-only metalinks                            | The firewall closes outgoing port 80. Fedora's mirror list also offers plain-HTTP and rsync mirrors. `/etc/dnf/repos.override.d/50-kasten-https.repo` asks for HTTPS mirrors only (`protocol=https`) for `fedora` and `updates`, and turns off `fedora-cisco-openh264`, which Kasten does not use                                                                                                                                                                                                                                                                                                                                                                                                                                     |

## The acceptance test

`deploy/test/run.sh all` runs every stage on a Linux Docker VM, then removes everything it created. Its VPS is a Fedora 45 container (`test/Dockerfile.fedora`) with systemd as PID 1 and nested rootless Podman as the kasten user. The Tang host and the client stay Debian 13 containers (`test/Dockerfile`). Its containers run systemd with `systemd-binfmt` masked, because binfmt_misc belongs to the whole VM: an unmasked systemd-binfmt in a privileged container clears the VM's handlers, Rosetta for example, when the container starts and stops. The test compares the VM's handlers before and after.

A container is not a VPS. These changes exist only for the container. `test/Dockerfile.fedora` makes the first four; `run.sh` makes the others:

- a unit that runs `mount --make-rshared /` before `sysinit.target` (`test/standin/kasten-deploytest-rshared.service`). Docker leaves `/` private, while a real host's `/` is shared, and only a shared `/` lets the containers see the volume that an unlock mounts;
- `rpm --setcaps shadow-utils`, because the image's layers lost the file capabilities of `newuidmap` and `newgidmap`, which rootless Podman needs;
- `/etc/shadow` with mode 0400, because the AppArmor profile for `unix_chkpwd` in Colima's Ubuntu VM would otherwise make PAM refuse the kasten user's manager;
- `dbus-broker`, `systemd-pam` and `systemd-udev`, which every real Fedora host has and the container image lacks;
- `net.ipv4.ip_unprivileged_port_start` set back to the kernel's 1024 in the VPS before install.sh, because Docker sets 0;
- Docker volumes for `/home` and `/var/lib`, so that Podman's storage is not on overlayfs;
- the marker file `/etc/kasten/test-without-selinux`, because the container cannot enforce SELinux. See [install.sh](#installsh);
- the lines of `test/mail.env`, which `run.sh` appends to `/opt/kasten/.env`: Unbound forwards every name to Docker's DNS, and the mail container trusts the SES stand-in's test CA. See [Limits](#limits).

The Fedora port also keeps the Debian test's other container-only changes: udev masked, device-mapper without udev (`DM_DISABLE_UDEV=1`), loop device nodes created at boot, a stand-in `tailscaled.service`, and the `swap` step skipped.

The test needs these things:

- a Linux Docker engine that allows privileged containers, with the `dm_crypt` and `loop` kernel modules loaded. If it is not your default engine, set `DOCKER_CONTEXT` to it;
- `jq` on your computer;
- for the `server` stage, a `kasten-server` image for the engine's architecture. The test uses the tag `dev-arm64`, or the tag in `KASTEN_TEST_SERVER_IMAGE_TAG`. It builds the `kasten-cli` image itself;
- the Mailpit and Alpine images that the repository root's `compose.yaml` (the dev stack's outbox) and `dev/outbox/make-dev-ca.sh` pin. Docker pulls them if they are missing. The Alpine container downloads `openssl` to make the SES stand-in's test certificate;
- the Fedora 45 image that `test/Dockerfile.fedora` pins by digest. Docker pulls it if it is missing. In the VPS container, install.sh downloads its packages from Fedora's mirrors, as on a real host.

```sh

KASTEN_TEST_SERVER_IMAGE_TAG=test deploy/test/run.sh all
```

`deploy/test/run.sh up install ...` runs the named stages in order. `all` runs `up`, then the stages in the order of the table below, then `down`, also after a stage that stops the script early. The container cannot test SELinux, the real kernel or a reboot of a VM. The Lima stages in `test/lima/` cover them, in Fedora Cloud VMs for aarch64 with enforcing SELinux and without the marker file. `test/lima/f45.yaml` gives the Fedora 45 VM 1 GiB of memory, like the 1 GB VPS. Both passed on 6 November 2026, with Lima 2.2.1 and its `vz` driver:

- `f45`: install.sh under enforcing SELinux, and its refusal and `kasten-podman`'s in permissive mode; the MCS separation of the mail and CLI containers; the first boot with the recovery passphrase; a backup and a restore; a lock while mail runs and 0, 1, 2, 4, 8 and 20 seconds into a start; the memory limits, the journald logs, the health check and Podman's restart after `kill -9`; the canary scan of every disk file system; a lock during `kasten-cli check`; and a reboot and a poweroff. It passed 213 checks, with 0 failures, in 545 s. With the dontaudit rules off, SELinux logged 1627 denials besides the one that the MCS check provokes on purpose; none was container-related apart from [the known one](../docs/security.md#container-isolation-on-the-host). It also measured the memory of the mail server, a dnf5-automatic run and a full `kasten-cli check` at the same time, beside `tailscaled`: see [Limits](#limits).
- `upgrade`: Kasten installed on Fedora 44, with the first boot, two deliveries, `kasten-cli check`, a backup and a restore there, then [the Fedora release upgrade](../docs/operations.md#the-fedora-release-upgrade) to Fedora 45, step by step. The volume stayed locked across both reboots, and no mail container existed before mail was turned on again. After that, it checked the unlock, `kasten-cli setup` with `0 changed`, the SMTP banner and both images, delivered a second canary message on Fedora 45, and found neither canary message on a disk file system. It passed 161 checks, with 0 failures, in 620 s. SELinux logged 527 denials, none container-related apart from the known one. Policy updates turned the dontaudit rules back on in step 2 and during the upgrade to Fedora 45; the stage turned them off again in step 2 and in step 5. The journal is in RAM, so the count does not include the boot that ran the offline transaction.

Run them on an Apple silicon Mac, from the repository root:

```sh
LIMA_HOME=~/scratch/kasten/lima deploy/test/lima/f45.sh all
LIMA_HOME=~/scratch/kasten/lima deploy/test/lima/upgrade.sh all
```

They need these things:

- Lima 2.x with its `vz` driver; the templates require 2.0.0 or later;
- `jq` on your computer;
- 1 GiB of memory, 2 vCPUs and a 20 GiB disk for each VM;
- Docker whose current context holds the arm64 image `kasten-server:dev-arm64`, or the image that `KASTEN_TEST_SERVER_IMAGE` names. They build the `kasten-cli` image from the checkout;
- `LIMA_HOME`, a short directory of the test's own. Lima keeps UNIX sockets there, and macOS limits their paths to 104 bytes, so `LIMA_HOME` and the VM's name together may have at most 70 bytes.

`f45.sh <stage>...` and `upgrade.sh <stage>...` run the named stages in order. `f45.sh` has the stages `up gate install images firstboot mcs pins serve check backup lock a2 a3 a4 a8 reboot final down`, and `upgrade.sh` has `up install images firstboot pins serve check backup bootlog step2 step3 step4 step5 step6 final down`. An unknown stage name exits with status 2. `all` runs every stage, then deletes the VM, unless `KASTEN_LIMA_KEEP=1`. `KASTEN_LIMA_VM` names the VM (`kasten-f45` or `kasten-upgrade` by default), `KASTEN_LIMA_OUT` the folder for the VM's notes (`$LIMA_HOME/<vm>.out` by default), and `KASTEN_LIMA_DEPLOY` another `deploy/` directory to install. `f45.yaml` and `f44.yaml` pin the images `Fedora-Cloud-Base-Generic-45-1.4.aarch64.qcow2` and `Fedora-Cloud-Base-Generic-44-1.7.aarch64.qcow2` by the SHA-256 digests in Fedora's signed CHECKSUM files.

A Lima VM still differs from the VPS. It is aarch64 on Apple's Virtualization framework, not amd64 on KVM. SSH comes in over vsock, so install.sh gets `--admin-ips` with Lima's network in place of Tailscale. There is no Tang: the recovery passphrase unlocks, and at boot `kasten-unlock.service` finds no Tang binding and fails with exit status 6, without a retry. There is no SES, no ACME and no SMTP client on the internet. Lima's network answers DNS only at its gateway, so Unbound forwards every name to systemd-resolved (`KASTEN_DEV_DNS_FORWARD=.`). The stages turn the dontaudit rules off, so that every SELinux denial is logged, and `final` turns them on again.

## Limits

- The root file system holds the sparse volume file and the OS. Podman's images are in `/home/kasten/.local/share/containers/storage`, on the same file system unless `/home` is a separate one. `auto` sizes the volume as the root file system's free space at install time minus 6 GiB. Every upgrade loads new images: remove the previous ones once the checks after the upgrade pass, with `kasten-podman image rm localhost/kasten-server:<old version> localhost/kasten-cli:<old version>`. The [weekly check](../docs/operations.md#weekly-checks) measures free space on `/`; when it runs out, writes inside the volume fail as I/O errors.
- `deploy/test/run.sh` runs in containers on one VM. It cannot test SELinux, zram, disk swap, a real reboot of a VM, udev, a real Tailscale join or the provider's network. The Lima stages cover SELinux, the real kernel, zram and a reboot of a VM, on aarch64 only. Production is amd64: no test has run on amd64, on real KVM, or on Hetzner's or netcup's images, and Tailscale has not yet run on Fedora. These are not yet tested on a real VPS. On the VPS, install.sh stops unless SELinux is enforcing, zram swap is active, no disk swap is on and no syslog daemon is installed. [Other checks before real mail](../docs/operations.md#other-checks-before-real-mail) covers the real reboot, and checks swap, the journal's location and syslog after it. The install guide's Tailscale and port-25 steps fail visibly without a working tailnet or provider network. No check covers udev on its own. A volume that does not unlock keeps mail stopped, so the mail monitors alert.
- The 1 GB memory budget is measured only in the Lima VMs, with 1 GiB and with `tailscaled` running but not signed in. The real 1 GB server is not yet measured. On 6 November 2026, in the final `f45` run (938 MiB total), a dnf5-automatic run changed 94 packages in 55 s while mail ran and `kasten-cli check --full` ran 87 times, each time passing. The peaks, sampled five times a second, were 776 of 938 MiB in use, 365 MiB of zram swap, 98 MiB for mail (113 MiB by its `memory.peak`), 126 MiB for the other containers, 310 MiB for dnf5-automatic (systemd: 322.7M, and 259.4M of swap) and 50 MiB for tailscaled. The lowest `MemAvailable` was 162 MiB, and 159 to 173 MiB in four such runs, against the acceptance line of 150 MiB. Nothing was killed for lack of memory, and mail stayed healthy without a restart. A `MemoryHigh=` cap of 256, 192 or 128 MiB on `dnf5-automatic.service` left the minimum at 150 to 163 MiB in four more runs and made the update up to 2.2 times slower, so Kasten ships none ([operations](../docs/operations.md#fedora-updates-and-the-web-app)). In the `upgrade` stage, `dnf5 -y upgrade --refresh` with mail running took 71 s and peaked at 678 MiB in use and 152 MiB of swap, and the download of Fedora 45 at 483 MiB in use.
- The test uses Stalwart's dev-mode HTTP listener on `127.0.0.1:8080`, because production's ACME certificate needs a real certificate authority and public DNS. Production's HTTP mode (ACME TLS-ALPN-01 on port 443, the admin listener on `127.0.0.1:8080`) is not yet tested on a real VPS. The test's Unbound forwards to Docker's DNS, because the development network blocks port 53, so Unbound's recursion with DNSSEC on the VPS is not yet tested either.
- The `probe` stage uses Mailpit as SES, with a test CA that only the test's mail container trusts (`KASTEN_EXTRA_CA_FILE`, a development-only setting). Real SES, its sandbox rules and the way back through the public MX are not tested.
- `kasten-check` now invokes one aggregate `kasten check` so one failing account keeps the combined Kuma status down. The off-host observer runs the same aggregate command.
