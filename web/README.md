# Kasten web app

The web app is a static PWA. It decrypts mail on the device, keeps an encrypted copy for offline reading and search, and sends through your server's JMAP. The `kasten-web` image serves it from an unprivileged nginx with the response headers the contract requires ([docs/architecture.md](../docs/architecture.md#the-web-app)). The look follows [DESIGN.md](DESIGN.md).

## Commands

Run these from the repository root.

| Command                                                          | Does                                                                          |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `pnpm --filter @kasten/web build`                                | Builds `web/dist`: the page, the key worker, the service worker, the licences |
| `pnpm --filter @kasten/web typecheck`                            | `tsc` on `src/`, then on the scripts, tests and e2e specs                     |
| `pnpm --filter @kasten/web test`                                 | Vitest unit tests in `web/test/`; no browser, no network                      |
| `pnpm --filter @kasten/web test:e2e`                             | Playwright in Chromium and WebKit against the running dev stack               |
| `pnpm --filter @kasten/web test:image`                           | Builds the `kasten-web` image and tests its start script with `docker run`    |
| `docker compose -p kasten-dev up -d --build web`                 | Rebuilds and restarts the app on <http://localhost:7480>                      |
| `node web/scripts/dev-reset-key.ts`                              | Removes the dev user's server key, so first-run key setup can run again       |
| `pnpm exec oxlint --deny-warnings web` and `pnpm exec oxfmt web` | Lint and format                                                               |

Set `DOCKER_CONTEXT` before the `docker compose` command if the dev stack runs on a Docker engine that is not your default. `./kasten dev up` also rebuilds and restarts the app.

After `dev-reset-key.ts`, also clear the site data in the browser (or use **Clear this device** in Settings). Mail stored while the old key was set stays encrypted to it, so this device shows it as "can't decrypt".

| `src/sync/search-index.ts`            | The local search index in segments of up to 500 messages, each saved as its own encrypted `kv` record                                                                                        |
| `src/store/`                          | The encrypted local store over IndexedDB                                                                                                                                                     |
| `src/worker/`                         | The key worker and its typed RPC                                                                                                                                                             |
| Page memory, during a passkey request | The passkey's PRF output, from the browser's answer until the page transfers it to the key worker, which wipes it after use. `navigator.credentials` exists only on the page, not in workers |

Locking ends the worker, which takes both keys with it. Before that, the app saves an open draft and the search index. The app locks after the idle time set in Settings (15 minutes unless changed), unless this device is kept unlocked.

**Keep unlocked on this device**, on the unlock screen or in Settings, saves an unlock on this device. The unlock screen ticks it by default, so after one unlock the app opens straight into the mail at each start; untick it to be asked every time. While the saved unlock runs, the app shows its start screen, not the passphrase form. The key worker encrypts the passphrase with a new device key that the browser creates as non-extractable, and the app stores both in `meta`. At each start the app then unlocks by itself, also offline, and it does not lock when idle. The passphrase no longer protects this device's copy of your key and mail: anyone who can open the device can read them, and so can someone who copies the browser's profile from its disk. The saved unlock ends with **Lock now** (in the account menu or in Settings), with turning the setting off, with sign-out, when the server ends the sign-in and the app finds out, with a new or restored key, and with **Clear this device**. The reload after an update keeps it. If it no longer opens, the app says so and asks for the passphrase.

When you sign out, or the server ends the sign-in, the app removes the sealed refresh token. A start without one shows **Sign in** first, and asks for the passphrase once, after the sign-in comes back. The app reads only whether the record exists; it stays sealed. The server can also end the sign-in while the app is locked, for example when the operator runs `kasten lock`. Then only the next unlock finds out, because the token is sealed. That one time, the app asks for the passphrase, then for the sign-in, then for the passphrase again: the sign-in page's return reloads the app, which ends the key worker.

Tabs share refresh-token rotation through a Web Lock scoped to the API, OAuth client and account. Each refresh reads the newest encrypted token inside that lock. Missing or changed account state ends the sign-in instead of reusing a stale token; sign-out uses the same lock.

The compose fields and the recovery-sheet text field turn off the browser's form restore and autofill (`autocomplete="off"`), so what you type stays out of the browser's saved session. localStorage, cookies and, after sign-in ends or is abandoned, sessionStorage hold nothing. `e2e/storage-audit.spec.ts` checks all of this in both browsers, and searches every file of the browser profile.

**Clear this device** deletes both databases, Cache Storage and sessionStorage, ends this browser's push subscription, closes Kasten's notifications and removes the service worker. It does not destroy the server's `PushSubscription` record: Stalwart keeps it until it expires, within 7 days, but cannot reach this browser any more.

Without persistent storage (`navigator.storage.persist()` not granted), the browser can remove all of Kasten's site data. That includes the wrapped key, the sealed sign-in, the device-only drafts and the Outbox, not only saved mail. The device then has to sign in again and unlock with the passphrase, from the key on the server, or restore the key from the recovery sheet when the server has no copy. Drafts and unsent mail that existed only on that device are lost. Settings > This device says this unless the browser has granted persistent storage.

## Message frames

Message HTML is sanitised with DOMPurify and shown in an iframe sandboxed without `allow-scripts`. The frame loads one of two static documents from the app's own origin. Each has its own CSP header from `kasten-web`:

| Document                     | `img-src`            | Used for                                  |
| ---------------------------- | -------------------- | ----------------------------------------- |
| `/frame/message.html`        | `data: blob:`        | Every message, with remote images removed |
| `/frame/message-remote.html` | `data: blob: https:` | One message after its **Show** action     |

Both policies allow the mail's inline styles, the images in the table and `data:` fonts, and nothing else: no scripts, no remote CSS or fonts, no media, no forms. `frame-ancestors 'self'` lets only the app frame them. The sandbox has `allow-same-origin`, so the page can write the sanitised content into the frame's document, where the frame's own CSP applies.

The CSP is the second line of defence. The sanitiser (`src/lib/sanitize.ts`) makes sure the frame never even asks for something it must not load:

- It runs once the frame document has loaded, with DOMPurify bound to the frame's own window. Chromium gives a parsed document the policy of the window that parsed it; parsed on the page, hostile mail would trip the app's CSP for every script and style it holds.
- The browser's URL parser reads every URL against the frame's address (`src/lib/mail-url.ts`), so spaces, control characters, backslashes and odd letter case read as the browser reads them. `data:` stays; `cid:` becomes the `blob:` URL of the message's own part, or goes if the part is missing; remote images go and are counted for "Remote images blocked" until **Show**, and then only `https` stays. Everything else goes: script URLs, `blob:` URLs written in the mail, relative URLs.
- CSS in `<style>` elements and style attributes is parsed by the browser (CSSOM) and written back, so escapes and forms such as `image-set("…")` in a parsed value cannot hide a URL. A value with `var()`, `env()`, `attr()`, `if()`, `inherit()` or a custom function keeps its raw text until the frame substitutes it: escapes, comments and single quotes stay. Such a name inside a string or `url("…")` is text, so a remote image at `…/a--b/c(1).gif(2).png` counts like any other; a value with a comment or a single quote counts every name in it, to be safe. A value with an escape counts as raw text, because an escape can spell the function's name, as in `v\61r(`, and it goes. Such a declaration goes when it holds `url(`, an image function, `src(`, a quote or an escape. A shorthand such as `background: var(…)` keeps that text on the shorthand, and goes on the same terms. When another declaration sets one of its longhands, the browser no longer shows the text, so the shorthand goes. These URLs go in both frames and are not counted for "Remote images blocked", because **Show** could not load them. `@import`, `@font-face` with a remote source, `@property`, `@counter-style` and other rules that are not needed to show mail go, and so do custom properties that could carry a URL. A last check drops any rule that still names another URL.
- `srcset` never stays (images show through `src`); `src` stays only on `<img>`; SVG attributes such as `fill` or `mask` keep only references to the message's own elements; a value with `url()`, `image-set()`, `image()`, `cross-fade()` or an escape goes.
- Forms, inputs, buttons, `<base>`, `<meta>`, `<link>`, frames, objects and embeds go. Links open in a new tab with `noopener noreferrer`; only `http`, `https`, `mailto`, `tel` and in-message `#` anchors stay links.

After sanitising, correspondence is restyled as a letter in the app's own type and colours, and designed mail keeps its card (`src/ui/letter.ts`, DESIGN.md "Thread"). That step only reads computed styles, then writes plain values (`transparent`, `inherit`, the app's own colours and sizes) through CSSOM and one appended rule set in the frame's single `<style>`; it adds no URL, element or loadable value, and mail of more than 1,500 elements keeps its card.

`e2e/hostile.spec.ts` checks before **Show** that the frame holds no canary URL in its CSS or in any attribute except a link's `href`, a check that does not depend on the CSP. It also checks that both frame documents serve their CSP, and `image-test/kasten-web-start.test.ts` checks those frame headers in the image.

The contract's first design used a `blob:` frame. A blob or srcdoc document inherits the app's CSP instead of its own:

- Chromium then drops every inline style of the mail (`style-src 'self'`).
- WebKit refuses to show the frame at all, because the inherited `frame-ancestors 'none'` applies.

The app's own policy therefore has `frame-src 'self'` instead of `frame-src blob:`.

Attachments are saved, never opened: the app hands the browser an `application/octet-stream` blob under a safe name (`src/lib/files.ts`: no path, no control characters, bidi overrides, isolates, marks or zero-width characters, no reserved device names, at most 150 characters). Only PNG, JPEG, GIF, WebP and AVIF parts get a preview, always as an `<img>`.

## Updates

The service worker precaches the app shell. A new deploy goes live by itself, without a button. The browser finds the new worker when the app loads, or when an installed app comes back into view (at most once a minute). Once the new worker has cached its shell, it asks every open page. A page that an earlier worker served, or that a hard reload loaded beside one, answers that it will reload, and asks for the takeover at its next quiet moment: no sign-in or key setup in progress (they keep their state only in the page), no sign-in code enrolment, sign-out or Clear this device running, no sign-in renewal, no message being prepared or sent, no mail change still saving or offering Undo, and, while the app is in view, no draft open and no text typed into a focused field. A device that is not kept unlocked would ask for the passphrase after the reload, so there the reload waits for the next lock (the idle lock or Lock now) or for the app to close. Pages of earlier versions cannot answer, so after 3 seconds without an answer the new worker takes over at once (`skipWaiting`, then `clients.claim`); a first install asks no one. A failed install deletes its cache and leaves the old version running. Every Kasten page that a worker served before then locks, which saves an open draft and ends its key worker, and reloads into the new version, at once for pages of earlier versions and at the next quiet moment otherwise. Until then such a page keeps running the previous version: activation keeps the shell that was live until then, and the worker serves a missing `/assets/` file from it. A device kept unlocked opens straight into the mail again. A fresh install's first worker takes over a page of its own version, so nothing reloads then. `e2e/update.spec.ts` checks, with two open signed-out pages of this version, that both reload into the new version without a click and that the new version does not reload again. Its update check is the test's own `registration.update()`, so the checks at load and on coming back into view, a page of an earlier version, the lock and the draft save at the takeover are not tested there.

A change to the response headers alone also updates the app. `kasten-web` serves `/sw.js` as the built worker plus a digest of its header configuration. A new `KASTEN_API_URL` or any CSP change therefore installs a new worker, which takes over and caches the page and the frames again with the new headers. No device needs its site data cleared after the API host moves. A restart with the same settings changes nothing. `test:image` checks the served `/sw.js`; that an installed app then takes the new headers is not yet tested in a browser.

## Notifications

While unlocked, the app checks its server subscription every 12 hours, including with **Never** selected for automatic locking. A foreground, focus or network-recovery event checks again after browser suspension. A check at least 12 hours after the last renewal extends the subscription to the full 7 days, so notifications stop 6.5 to 7 days after the last check, which runs only while unlocked. A failed check shows an error and retries after one minute, backing off to at most an hour. Locking stops these checks; unlocking resumes them. A closed or suspended browser cannot guarantee renewal, so opening the app recreates an expired server subscription.

**Turn on notifications** in Settings subscribes this device to new-mail pushes from your server. **Show sender and subject in notifications** is on unless you turn it off:

| Setting | The subscription asks the server for                | A notification shows                                                                                                                                                                               |
| ------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| On      | `emailPush` with `from` and `subject`               | The sender as the title, the subject below. A plain state change, such as a message sent from this or another device or an IMAP append, shows a quiet "Mailbox updated" notice with "No new mail." |
| Off     | No `emailPush`: Stalwart sends a plain state change | "New mail" only, for every push, including the state change of each message sent                                                                                                                   |

Stalwart sends the Drafts and Sent copies of a send as the same plain state change as a delivery. So on a device with the setting off, or on every device when the server lacks `urn:ietf:params:jmap:emailpush`, each message sent from any device of the account shows "New mail". The "Mailbox updated" notice names no one and replaces only the previous one of its kind. Each new-mail notification has its own tag, so a new one never replaces or silences an earlier one.

Turning the setting off also closes all of Kasten's new-mail notifications that are still on screen. Changing the setting ends the browser's push subscription and makes a new one, with a new endpoint. The same call to the server destroys the old subscription. If that fails, for example offline, the app makes it again on the next start. The service worker cannot read the encrypted store, so the app also writes this setting to `kasten-sw`, before it changes the subscription. The service worker applies the setting to every push, including one that is still on its way from the old subscription. If it cannot read the setting, it shows "New mail" only. The app also writes to `kasten-sw` whether the subscription asks for `emailPush`, before it creates the subscription and at each check. If the service worker cannot read that value, it counts it as no, so every push then shows as new mail. The verification push after each new subscription always says "Notifications are on".

Signing out ends this device's subscription, in the browser and on the server, and closes Kasten's new-mail notifications. The next sign-in on this device subscribes again, unless notifications were turned off here. If ending the subscription fails, the app says "You're signed out, but notifications may still arrive here. Turn them off in your browser's settings." **Stop notifications on other devices** in Settings destroys the account's other subscriptions, for a lost device. A device whose sign-in is still valid subscribes again at its next check, which runs while Kasten is unlocked there.

## Sending and the Outbox

**Send** builds the message in the key worker (`buildMessage` and `createOutboxEntry` from `@kasten/core`), saves the outbox entry encrypted, deletes the draft and runs the outbox. The worker runs `processOutboxEntry`. It asks the page to save the entry just before it submits and again once the server accepted it, so an app that stops mid-send never sends twice.

| Outbox shows                                             | Means                                                                                                                                                       | The app                                                                        |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Sending…                                                 | The flow is running                                                                                                                                         | Waits                                                                          |
| Waiting to send                                          | Offline, or a temporary failure                                                                                                                             | Retries on reconnect, then after 15 s to 5 min                                 |
| Send failed: Retry                                       | The server refused it, for example its recipients (the SMTP replies are listed)                                                                             | Waits for **Retry**                                                            |
| Not sure it was sent                                     | The submit request got no clear answer, and Kasten found no submission record for it, or the server failed after it may have queued it (core's `uncertain`) | Asks before **Send again** (`requeue`)                                         |
| Sent. Saving the encrypted copy…                         | Sent; the encrypted Sent copy is not stored yet                                                                                                             | Retries the copy only                                                          |
| Sent, but some recipients were refused                   | The server sent it to the others but refused these recipients (the SMTP replies are listed); it does not retry them                                         | Keeps it until **Dismiss** and never sends it again                            |
| Sent. Deleting the unencrypted copy from your server…    | Sent; the plaintext draft that a failed cleanup left on the server is not deleted yet                                                                       | Retries the delete, then removes the entry; **Dismiss** deletes the copy first |
| Deleted. Deleting the unencrypted copy from your server… | You deleted it while the plaintext draft that a failed cleanup left was still on the server                                                                 | Never sends it; retries the delete, then removes the entry                     |

Only one tab runs the outbox at a time (a Web Lock), and each entry is read again just before it is processed, so a message deleted from the Outbox, or sent by another tab, is never sent again. An uncertain entry is processed once per run too: core looks for the plaintext draft the submit may have left on the server, asks whether the server has a submission for it, and only then destroys it. Core marks the message sent only if the server has its submission; otherwise the entry stays "Not sure it was sent" until you choose **Send again**. A run that leaves a plaintext draft on the server schedules the next run, also for an entry it does not send again.

A sent message stays in the Outbox only while some of its recipients were refused, or while its plaintext draft is still on the server. **Delete** on a message whose plaintext draft is still on the server marks it deleted before it deletes the draft. If that delete fails, the message stays, is never sent, and goes once a later run deletes the draft. The sidebar's "waiting" count leaves sent and deleted messages out.

Drafts stay on the device, encrypted. The server never holds one except during the submit request. If the app cannot delete the submit's plaintext draft then, a later outbox run deletes it.

## Search

The search field searches this device only: the encrypted index, decrypted in memory. Until every message is decrypted and indexed, the results say "Searched N of M messages". Free words go to the index; these operators filter the results:

| Operator         | Matches                                                  |
| ---------------- | -------------------------------------------------------- |
| `from:sam`       | Sender name or address                                   |
| `to:priya`       | To and Cc names or addresses                             |
| `subject:"box"`  | Words in the subject                                     |
| `has:attachment` | Messages with attachments                                |
| `in:archive`     | A folder by name or role word (inbox, sent, spam, trash) |

## The `kasten-web` image

Build it from the repository root: `docker build -f web/Dockerfile -t kasten-web .`. It serves plain HTTP on port 8080 as user 101. Put it behind an HTTPS proxy that passes its response headers unchanged.

`docker/kasten-web-start` writes the headers, `/config.json` and the served `/sw.js` at start. The served `/sw.js` is the built worker plus one comment line, `// kasten-web headers <sha256>`, a digest of the nginx configuration that sets every header ([Updates](#updates)). Every response carries `X-Robots-Tag: noindex, nofollow`, so search engines leave the app out of their results, and `Strict-Transport-Security: max-age=31536000`, so browsers that have seen the app reach it only over HTTPS for a year.

| Variable                    | Required              | Meaning                                                                                                                                                                                                                                                                      |
| --------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `KASTEN_API_URL`            | Yes                   | The mail API's origin, `https://<mailApiHostname>`, for example `https://mail.example.com`. It must use `https`, except for localhost. `connect-src` is `'self'` plus this origin                                                                                            |
| `KASTEN_WEB_CONFIG_FILE`    | No                    | A ready `config.json` (default `/etc/kasten-web/config.json`). If that file exists, the image serves it, and its `apiUrl` must equal `KASTEN_API_URL`                                                                                                                        |
| `KASTEN_OAUTH_CLIENT_ID`    | Without a config file | The OAuth client ID: `webApp.oauthClientId` from `kasten.json`, for example `kasten-web`                                                                                                                                                                                     |
| `KASTEN_OPERATOR_KEYS_FILE` | Without a config file | A file of armored public keys, added to every user's key bundle. Use the key of `operatorPublicKeyFile` in `kasten.json`: without it, `kasten lock` refuses the key set that the app uploads. The image itself starts without it. It refuses a file that holds a private key |
| `KASTEN_APP_NAME`           | No                    | The app's name (default Kasten)                                                                                                                                                                                                                                              |

Without a config file, the image writes `/config.json` as `{"apiUrl", "oauthClientId", "operatorKeys": [armored keys], "appName"}` from these variables. On a wrong value, it prints the reason and exits with status 2.

`pnpm --filter @kasten/web test:image` checks this in the real image. It builds `kasten-web:image-test` from the current source, then uses `docker run` to check the written and the mounted `/config.json`, the response headers, including the CSP of both message frames, and every refusal. It checks `/sw.js` too: the same settings give the same bytes, and another `KASTEN_API_URL` gives different bytes. It passes its files through a Docker volume, publishes ephemeral ports on `127.0.0.1` only, and removes its containers, volume and image tag at the end. It uses `DOCKER_CONTEXT` from your environment, or else the one in `.kasten-dev/state.json`.

The root filesystem can be read-only; nginx writes only to `/tmp`, which must be writable (a tmpfs).

The image also serves `/THIRD_PARTY_LICENSES.txt`, which the build writes from the bundled packages (`scripts/licenses.ts`). It names each package's licence and source, with OpenPGP.js's source at the tag of the bundled version, and ends with the GNU GPL, version 3, on which OpenPGP.js's LGPL builds. **Settings** > **About** links to it. The service worker leaves that page to the network, so it opens as text, not as the app. The link has not yet been checked in a browser.

## End-to-end tests

The specs in `e2e/` need the dev stack from `./kasten dev up`, with the `web` service built from the current source (see [Commands](#commands)). They also need Playwright's browsers, installed once with `pnpm --filter @kasten/web exec playwright install chromium webkit`. They use `you@kasten.test` and reset its server key before and after each file, so run them one at a time (the config uses one worker).

They can also run against an isolated stack ([dev/README.md](../dev/README.md#a-second-isolated-stack)) with `KASTEN_DEV_PORT_BASE=7480`. Set the same four variables for `test:e2e`, and run the `web` image on port 7480 yourself, because an isolated stack has none. The specs read the SMTP port and everything else from that stack's `state.json`.

The hostile corpus is built fresh for each run by `e2e/hostile-corpus.ts`: script tags, event handlers, script and data URLs, frames and embeds, `<base>`, meta refresh and forms, remote CSS in every form (escapes, single-quoted image functions and quotes in comments inside `var()`, `env()` and `if()`, shorthands whose text a later longhand hides, `image-set`, `@font-face`, grouped and nested rules, custom properties, SVG `mask` values), CSS exfiltration selectors, a missing `cid:` part, a remote image whose URL looks like a substitution function (`a--b/c(1).gif(2)`), which **Show** must still offer and load, 10,000 nested elements, a 5 MB HTML part, an HTML attachment, dangerous file names and a Content-Type spoof. Its URLs point at `e2e/canary.ts`: an HTTP and an HTTPS server on `127.0.0.1` with ports the system picks, which record every request and connection. `e2e/deliver.ts` sends the corpus over SMTP and files it into a folder of its own.

`KASTEN_SCREENS=<folder>` saves screenshots there (default `web/test-results/screens`).

A full run delivers the dev mail eight times, the hostile corpus four times and the large message twice to `you@kasten.test` over SMTP. Kasten's sender throttle allows 100 messages an hour from one IP address and sender domain to one recipient, so several runs within an hour can hit `452 4.4.5 Rate limit exceeded` in `./kasten dev mail`; wait for the hour to pass. The hostile corpus uses a new sender domain on each run.

## Not verified here

- A real iPhone: Home Screen install, Safari's storage limits, push notifications and safe-area insets on a notched screen. WebKit at 390 × 844 in Playwright is the closest local check.
- Remote images over https from real senders: the dev mail's image hosts do not resolve. `hostile.spec.ts` loads images after **Show** from its local HTTPS canary instead.
- The service worker keeping a push verification code while no window is open: no push service runs locally, so `test/push-pending.test.ts` checks the lifetime, the read-once rule and the subscription replacement, and the storage audit checks that `kasten-sw` holds no code.
- A real push subscription and delivery: `e2e/notifications.spec.ts` gives the page a stand-in for the browser's push subscription and answers the `PushSubscription` calls itself, because headless browsers refuse notifications and Stalwart refuses local push endpoints. Its pushes reach the real service worker through Chrome's DevTools, so WebKit checks only the subscription requests.
- A real camera for the recovery-sheet scanner: `test/camera.test.ts` checks with stand-in streams that the camera turns off when the scanner closes before access is granted, when the QR decoder fails to load and when the scan cannot start.
- Where the operating system keeps notifications: macOS, Windows, Android and iOS may keep a shown notification's sender and subject in their notification centres until you dismiss it.
- WebKit's session-restore files: the WebKit profile in `storage-audit.spec.ts` writes no session files, so there the profile search covers IndexedDB and the caches only.
