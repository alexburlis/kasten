# Integration tests against the dev stack

```sh
./kasten dev up
pnpm test:integration
```

The tests talk to the running dev stack that `./kasten dev up` started. They read its addresses and credential file paths from `.kasten-dev/state.json` (or `$KASTEN_DEV_DIR/state.json`). Before any test runs, `global-setup.ts` checks that the state file exists, that Stalwart and the outbox answer, that the `mail` container is healthy and that the admin API key works. If any check fails, the run fails with the reason. No test is skipped, so a missing stack never looks like a pass.

They need Node 24, the repository's dev dependencies (`pnpm install`) and the `docker` CLI for the stack's engine. `DOCKER_CONTEXT` comes from your environment, or else from `state.json`.

All 16 files, 81 tests, passed on the local dev stack on 4 November 2026. They passed again on 5 November 2026, after that day's changes to `cli-read.test.ts` and `cli-import-membership.test.ts`. No test was skipped.

**CORS.** A preflight from `http://localhost:7480` gets status 204 and `Access-Control-Allow-Origin: http://localhost:7480`. Stalwart's CORS headers are static, so a request from another origin gets the same header, naming `http://localhost:7480`. It never names the caller's origin and is never `*`, so a browser on another origin refuses the response. The test checks that, for another origin, the header is absent or names `http://localhost:7480`, and is never the caller's origin or `*`.

## Their footprint

- Each test creates its own throwaway accounts (`it-<name>-<random>@kasten.test`) through the admin API and deletes them afterwards. No test uses the shared stack's `you@` or `sam@` or depends on another test's mail. The lock tests use a throwaway OAuth client, never `kasten-web`.
- `cli-domain-remove.test.ts` creates a throwaway domain `it-pilot-<random>.test` with one account and removes both.
- `cli-config-export.test.ts` changes the shared stack's `x:SpamPyzor.blockCount` by one for a moment and restores it, also in `afterAll` on failure. Its comparisons leave out `x:Account` and `x:OAuthClient`, which concurrent test files change.
- `cli-probe.test.ts` creates a second, isolated stack, Compose project `kasten-clitest` on ports 7600 to 7604, with its own `.kasten-dev` directory, and deletes it with `./kasten dev reset` at the end.
- Keys and other files for GnuPG go in a fresh directory under `.kasten-dev/tmp/`, which the test removes.
- The send-flow test deletes its messages from the outbox afterwards.
- Throwaway containers and volumes are named `kasten-it-*`, for example the Dovecot source of the import test, and removed at the end of their test.
- Up to three test files run at once. Their OAuth sign-ins count against Stalwart's rate limit for anonymous HTTP requests from one IP address, which all tests share. A test file that added three sign-ins once pushed the suite over it (`limit.too-many-requests` in the mail log), so new tests reuse sign-ins where they can. `cli-user-mfa.test.ts` adds one more throwaway OAuth client and two sign-ins: one sign-in with a code (TOTP), and the probe-account sign-in of `kasten lock`'s proof. With four files at once, the suite then went over the limit (`token exchange: HTTP 429` in `security.test.ts`), so it runs three. Above 100 anonymous requests a minute, Stalwart answers HTTP 429 with `Retry-After`. [`rate-limit.ts`](rate-limit.ts) waits that long and sends the request again, at most six times, and logs each wait. It does so in the test workers and, through `NODE_OPTIONS`, in the CLI processes the tests start; `runCli` moves those notices out of the CLI's stderr into the test log.
- Requests from this machine reach Stalwart from the default network's gateway, not from loopback. That matters: Stalwart lets loopback clients bypass `allowedEndpoints`, so a loopback test of the registration refusal would prove nothing.
