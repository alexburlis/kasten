# Architecture and build contract

This page is the contract between Kasten's parts. Change it first when a part's interface changes.

## Parts

| Part                                | Path             | Language                                     | Runs where                                         |
| ----------------------------------- | ---------------- | -------------------------------------------- | -------------------------------------------------- |
| Mail server image `kasten-server`   | `server/`        | Dockerfile, POSIX shell                      | The VPS (production); Docker on your machine (dev) |
| Web app and image `kasten-web`      | `web/`           | TypeScript, Preact, Vite                     | Browser; static files from any HTTPS host          |
| Shared library `@kasten/core`       | `packages/core/` | TypeScript, isomorphic (browser and Node 24) | Inside the web app and the CLI                     |
| CLI `kasten` and image `kasten-cli` | `cli/`           | TypeScript on Node 24                        | Operator machine, CI, or `kasten-cli` on the VPS   |
| Repo wrapper `./kasten`             | `kasten`         | POSIX shell                                  | Calls Docker Compose and the CLI image             |
| Production host files               | `deploy/`        | Shell, systemd, nftables                     | Fedora 45 VPS; Tang on a second host               |

No other server process, queue, scheduler or account backend exists. Stalwart is the only backend: SMTP, JMAP, OAuth sign-in, MFA, aliases, spam rules and at-rest encryption.

## Pinned upstream

- Stalwart **v1.0.1**, official release tarballs, SHA-256 pinned per architecture (`x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`). The sigstore identity is `https://github.com/stalwartlabs/stalwart/.github/workflows/ci.yml@refs/tags/v1.0.1`.
- Stalwart spam rules **v3.0.3**, SHA-256 pinned, loaded from a local `file://` URL. No runtime downloads.
- restic **0.19.1**, SHA-256 pinned.
- Base images pinned by digest in the Dockerfiles: `debian:trixie-slim` (`kasten-server`), `node:24-slim` (`kasten-cli`, and the `kasten-web` build stage) and `nginxinc/nginx-unprivileged:1.30.6-alpine-slim` (`kasten-web`).
- Stalwart configuration lives in its database. It is written only through the management API (`urn:stalwart:jmap`, `x:*` objects), never by editing files. `config.json` names only the SQLite store.

## Server behaviour that every part relies on

- **Encryption at rest.** `x:Email` singleton has `encryptAtRest: true` and `encryptOnAppend: true`. Each account's `x:AccountSettings.encryptionAtRest` points at one `x:PublicKey` holding the account's whole key bundle: one armored block per key, the user's key first, then the operator key that `kasten setup` requires (`operatorPublicKeyFile`). Keys are OpenPGP v4, Ed25519 primary with a Cv25519 encryption subkey, and no expiry on any key or subkey. `inspectKeyBundle` reports any other primary algorithm (RSA, NIST curves, RFC 9580 Ed25519) or transport-encryption subkey (anything but ECDH on Curve25519, including RFC 9580 X25519) as a problem, so `kasten keys set` and `kasten lock` refuse it, and the daily `kasten check` reports it as a finding.
- **What stays plaintext on purpose.** Stalwart stores JMAP `$draft` messages as-is, and messages its `is_encrypted` check treats as already protected. `@kasten/core` mirrors that check (`crypto.rs:355-404` in v1.0.1) and cites the exact lines.
- **Send flow** (proven on v1.0.1):
  1. Upload the plaintext RFC 5322 message. It has an explicit Message-ID, a References header that ends with its own Message-ID, and no Bcc header. Amazon SES delivers the message under a Message-ID of its own, so a reply cites the original ID only through References, and Stalwart threads the reply with the Sent copy (live proof: `packages/core/test/live/send.live.ts`, passed on the local dev stack on 4 November 2026).
  2. In one JMAP request: `Email/import` into Drafts with `$draft` and `$seen`, then `EmailSubmission/set` with `onSuccessDestroyEmail: ["#s"]`.
  3. If submission fails, destroy the draft in a follow-up request. Keep the message in the device's encrypted outbox and retry from there. If any destroy of that plaintext draft fails, after a refused submission or after a successful one whose `onSuccessDestroyEmail` failed, the outbox entry records the draft (`strayDraftId`). The app tries the destroy once more before it reports the message sent. Then every outbox run deletes the draft, also for entries it does not send again: sent ones, refused ones until the user presses Retry, and deleted ones. A run that leaves such a draft schedules the next run. For an `uncertain` entry, the run first asks whether the draft has an `EmailSubmission`, which marks the message sent, and destroys the draft only after that answer. When the answer is yes, the outbox first destroys the message's other drafts, then saves the entry as sent, and destroys that draft last. An earlier attempt can also leave a draft that the entry does not record, such as an `uncertain` one whose Drafts lookup failed before the user chose **Send again**. So once a message that had earlier attempts is saved as sent, the app looks in Drafts for its Message-ID and destroys every draft there. The first draft whose destroy fails is recorded in `strayDraftId`. If another one fails too, the Sent copy waits and the entry stays unfinished for the next run. Each later run first destroys the recorded draft and stops there while that fails; otherwise it looks again, until the Sent copy is stored, so a stop or a failed lookup before then is made up for. If the lookup fails on the run that stores the Sent copy, the draft stays until someone deletes it, and the daily `kasten check` reports it as `staleDraft` once it is an hour old. An `uncertain` entry also records only one draft. When one draft shows that the message went out but the destroy of another fails, the entry stays `uncertain` until a later lookup finds that draft again; if the user deletes the entry first, that draft stays until the daily check reports it. A sent entry stays in the Outbox until the draft is gone. Deleting or dismissing an entry deletes its draft first. While the server cannot be reached, the entry stays, marked deleted, and is never sent again. The key worker sends with the access token the page gave it. A step that the server refuses with HTTP 401 ran nothing, so the entry stays queued, and the outbox sends it again on its own after it forces a token refresh (live proof that a refused step runs nothing: `tests/integration/send-flow.test.ts`, passed on the local dev stack on 4 November 2026). A permanent refusal waits for the user's Retry.
  4. On success, build a PGP/MIME Sent copy encrypted to the account's key bundle. Its outer headers keep From, To, Cc, Subject, Date, Message-ID, In-Reply-To and References; Bcc goes inside the encrypted part. Then `Email/import` it into Sent with `$seen`.
  5. Before importing, look for an existing copy so a retry never duplicates it. Stalwart's default search index has no headers, so the app queries Sent by `receivedAt` within one minute of the send time, then compares Message-IDs.
  - Never use `onSuccessUpdateEmail`. Never submit without `$draft`.
- **Drafts** stay on the device only, in the encrypted local store. The server never holds a draft except during step 2, or until a failed cleanup is retried. A draft that a failed lookup misses, or that a deleted `uncertain` entry did not record, or that a `submitted` entry deleted while it waited after two failed destroys did not record, stays until someone deletes it; the daily check reports it after an hour.
- **Sign-in.** Stalwart's built-in OAuth: authorization code with PKCE (S256). The app sends the browser to Kasten's sign-in page, which Stalwart serves from the mail server at `/signin/` instead of its own `/login` page ([details](stalwart-v1.0.1.md#kastens-sign-in-page)). The page posts to Stalwart's `/api/auth` on the same origin, so the account password and sign-in codes never reach the app host. One admin-created OAuth client has exactly one redirect URI, the app's callback URL. The app requests exactly `openid offline_access urn:ietf:params:oauth:scope:mail` and always sends `state`. Access and refresh tokens stay in memory and the encrypted local store, never in `localStorage`.
- **What an app token can change.** v1.0.1 has no settings scope ([details](stalwart-v1.0.1.md#3-scopes-and-what-an-app-token-can-do)). While the OAuth client is `firstParty: true`, a token has the account's own full permissions, so the app can upload the key bundle and enrol TOTP. `kasten lock` sets `firstParty: false` and destroys the client's grants in the account it locks; run it once per account. From then on, an app token can use mail but gets `forbidden` on every `x:*` object, so a stolen session cannot change the key set or MFA, or create an app password. Before the lock, a stolen first-party session could replace the key set, so a first lock or a changed key set needs `--user-fingerprint`, the fingerprint on the owner's recovery sheet, and the user key must match it. App passwords and API keys keep their rights after the lock, so `kasten lock` pins nothing while the account has any that Kasten did not create; `--revoke-others` destroys them. Agents and the CLI can still change keys and create app passwords with the admin key (`kasten keys set`, `kasten app-password create`). `kasten user mfa` turns sign-in codes on and off without the app.
- **Public client registration** (`POST /auth/register`), device sign-in (`/auth/device`, `/device`) and Stalwart's built-in `/login` page are refused through `allowedEndpoints`. That rule fails open on a wrong-typed expression and does not apply to loopback clients, so `kasten security-check` tests it live from a non-loopback address.
- **CORS.** Exact-origin headers for the app's origin, through `x:Http.responseHeaders`. These headers are static: every response names the app's origin, whichever origin asked. Browsers enforce the match, so other sites still can't read responses. Checks assert that the allow header is never `*` and never echoes the caller's origin.
- **Admin.** The web admin UI and every `x:Application` bundle except Kasten's sign-in page are disabled. Management uses an IP-restricted admin API key (`Authorization: Bearer API_...`) for a key-only admin account, reachable only on the private path. In production that path is the plain-HTTP admin listener `127.0.0.1:8080`, and `admin.allowedIps` is `127.0.0.1/32` and `::1/128`. The CLI reaches it from the VPS itself (`kasten-cli`), or from the operator's computer through an SSH tunnel to that port. `STALWART_RECOVERY_ADMIN` is set only during the one first-boot recovery run (`kasten-server recovery`), never in normal runtime; Stalwart honours it in normal mode too while it is set. That run has no network: in production, `kasten-bootstrap` runs the container `kasten-recovery` with `--network=none` and `kasten setup --bootstrap` inside its network namespace (`--network=container:kasten-recovery`); in dev, `./kasten dev up` does the same with `docker run --network none`. Every normal run sets `STALWART_PUBLIC_URL` to the mail API's URL, which becomes the OAuth issuer and the base of every session URL.
- **App passwords** with `Inherit` permissions can change the key set. Every app password that Kasten issues gets an explicit `Replace` permission list: the agent reader's read-only list (`kasten reader create`), or the import list with exactly the IMAP commands that `import-imap` sends to the destination (`kasten app-password create --purpose import`). Stalwart answers an IMAP command outside the list with no response and ends the session.
- **Push.** Stalwart's own Web Push: `PushSubscription/set` with RFC 8291 keys, the VAPID `applicationServerKey` from the session capability `urn:ietf:params:jmap:webpush-vapid`, and types `EmailDelivery` only. While the device setting **Show sender and subject in notifications** is on (the default) and the session offers `urn:ietf:params:jmap:emailpush`, the subscription also asks for `emailPush` with `from` and `subject`. Without `emailPush`, Stalwart sends a plain state change. The service worker shows a notification for every push. Stalwart v1.0.1 also pushes a plain state change for every `Email/import` (the app's `$draft` and Sent copy), IMAP APPEND and `Email/set` create. While the subscription asks for `emailPush`, the app records that in `kasten-sw`, and the service worker shows only an `EmailPush` as new mail. A state change then gets a quiet "Mailbox updated" notice under its own tag. Without `emailPush`, a send looks like new mail. Each new-mail notification has its own tag. The verification push says "Notifications are on". For new mail, with the setting off or unreadable, it shows only "New mail". Changing the setting replaces the browser's push subscription, so the new one has a new endpoint. Stalwart limits a subscription to 7 days. While unlocked, the app checks the subscription at unlock, every 12 hours, and on focus or network recovery. A check at least 12 hours after the last renewal extends it to the full 7 days. Notifications therefore stop 6.5 to 7 days after the app's last check, and resume at the next unlock. Stalwart v1.0.1 keeps a subscription whose pushes fail (410 included) until it expires. Sign-out stops the checks, and no check starts again until mail starts after the next unlock or sign-in. It destroys this device's subscription after any check still running, and waits at most 5 seconds for both before it ends the key worker. Without a service worker registration, as after a failed first install, the browser has no subscription, so sign-out waits for neither. **Settings > Notifications > Stop notifications on other devices** destroys every other one. EventSource and downloads use `fetch()` with the bearer token, because `EventSource` cannot send an `Authorization` header.
- **Limits.** 40 MiB inbound SMTP, `Email.maxMessageSize` 38 MB for sending, `uploadTtl` 5 minutes, `maxUploadSize` 53.2 MB and `uploadQuota` 91.2 MB per 5-minute window, sized from the 38 MB send limit so the encrypted Sent copy (about 1.378 × the message) uploads in one pass (live proof: `packages/core/test/live/send.live.ts`, passed on the local dev stack on 4 November 2026), hourly blob and data cleanup, `maxBufferedMemory` 256 MiB, SQLite pool 4, a sender-IP throttle of 5 connections per second per IP, one sender-to-recipient throttle `{remoteIp, senderDomain, rcpt}` at 100/hour changed in place, 100 outbound recipients/day.
- **Turned off:** statistical spam training (server and account), stored MTA reports, calendar scheduling, ASN/GeoIP, the four remote lists of the spam rules (OpenPhish, PhishTank, disposable and free mail domains), outbound DMARC/TLS/DKIM/SPF reports, the web admin UI, remote redirect fetching, OAuth client metadata documents, DKIM signing (SES signs), the automatic deletion of mail in Deleted Items and Junk Mail after 30 days (`expungeTrashAfter`).
- **No runtime downloads.** The first recovery start tries to download the web admin UI; with no network it cannot. Bootstrap then stores the web admin UI, ASN/GeoIP and the four remote lists as disabled before the first normal start, so Stalwart downloads nothing from then on ([details](stalwart-v1.0.1.md#13-first-boot-without-downloads)).
- **Outbound route.** Non-local recipients select the sender domain’s identity-scoped `relays` entry and separate `ses-<domain>` route, SES on587, `startTls: require`, certificate verified, never `allowInvalidCerts`. Mail with an empty or unconfigured envelope sender, such as DSNs and vacation replies, takes the first domain's relay, `ses-<domains[0]>`. Nothing uses Stalwart's direct MX route, which matches the dropped outbound port 25 (live proof on the dev stack: `tests/integration/send-flow.test.ts`, passed on 4 November 2026). One accepted limit: community reports (re:Post "ses smtp rejects bounce messages from exim", not an AWS document) say that SES SMTP may refuse `MAIL FROM:<>` with 501. If so, DSNs to remote senders fail at once, visibly in the delivery log, instead of being delivered. A vacation reply From a second domain also fails under the first domain's identity-scoped IAM policy. Neither is yet tested on live SES; the pilot can confirm both. In dev, the relay is the local outbox catcher, and dev TLS uses a local dev CA that the server image trusts. Dev never weakens certificate checks.
- **Fail-closed data directory.** The server entrypoint refuses to start Stalwart unless the data directory carries the marker file that `kasten-server init` wrote, and the marker's volume id equals `KASTEN_VOLUME_ID` from the environment. A missing LUKS mount therefore leaves SMTP closed instead of creating an empty mailbox.
- **Logging.** `kasten setup` adds a stdout tracer at `info`, so the container log (and journald on the host) records delivery and `store.crypto-error` events. Info-level logs hold envelope addresses, client IP addresses, Message-IDs and blob ids, not subjects or bodies ([details](stalwart-v1.0.1.md#14-logging)).

## The web app

- Static bundle only. No third-party runtime scripts, fonts or analytics. All dependencies are pinned and bundled.
- Runtime config comes from `/config.json` on the app's own origin: `{ "apiUrl", "oauthClientId", "operatorKeys": [armored public keys], "appName" }`. At container start, the `kasten-web` image writes the CSP header from `KASTEN_API_URL`. It writes `config.json` from `KASTEN_API_URL`, `KASTEN_OAUTH_CLIENT_ID`, `KASTEN_OPERATOR_KEYS_FILE` and `KASTEN_APP_NAME`, or serves a mounted `config.json` whose `apiUrl` must equal `KASTEN_API_URL`. `kasten-web` also serves `/sw.js` with a digest of its header configuration. The cached page and frames keep their install-time headers, so a header-only change reaches installed apps through the normal update prompt.
- CSP: `default-src 'none'`, scripts, styles, workers and the manifest only from `'self'`, `connect-src` limited to `'self'` and `apiUrl`, `img-src 'self' blob: data:`, `frame-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'none'`.
- The private key lives only in a dedicated Web Worker. The UI thread sends ciphertext in and receives parsed messages out.
- Message HTML is sanitised with DOMPurify, called from the page but running in the message frame's realm: once the frame document has loaded, DOMPurify is bound to the frame's window. The HTML is therefore parsed under the frame's CSP, and URLs resolve against the frame's address. The result is written into one of two static same-origin frame pages, `/frame/message.html` or `/frame/message-remote.html` (after the user's per-message "Show remote images"). Each has its own CSP header from the `kasten-web` image. The iframe is sandboxed with `allow-same-origin allow-popups allow-popups-to-escape-sandbox` and never `allow-scripts`. A `blob:` or `srcdoc` frame would not work: it inherits the app's CSP, so Chromium drops the mail's inline styles and WebKit refuses to show it (reproduced).
- Local store: IndexedDB records encrypted with AES-GCM under a random data key. That key is wrapped by a key derived from the passphrase (PBKDF2-SHA-256 through WebCrypto). No plaintext mail, plaintext search index or unwrapped key ever reaches persistent storage. A device the user keeps unlocked also stores the passphrase, encrypted with AES-GCM under a non-extractable device key that IndexedDB keeps beside it; script can use that key but not read it.
- Search: a local index over decrypted bodies, persisted only in encrypted form. The index is kept in segments of up to 500 messages. Each segment is its own encrypted kv record, `search:<n>`, with the segment's message ids, its serialised index and its text-extraction version, so a save rewrites only the segments that changed, and an unlock loads them one at a time. Search merges the segments' hits by score. Each segment scores with its own term statistics, so the matches are the same as with one index, but the ranking can differ slightly. At start, the app indexes bodies that the saved index lacks again from the encrypted cache, without downloading them. The first start of this version deletes the single `search` record of earlier versions and rebuilds the index from cached bodies once. A failed index save shows a notice instead of being hidden. The app shows indexing coverage, for example "Indexed 1,234 of 26,343", until it is complete. A message whose decryption fails with an OpenPGP.js error (`decryptFailed`, `unreadableCiphertext`) is saved and shown with its reason, but is not indexed or counted. The next start downloads it once more. A second such failure keeps it like mail that can never be decrypted (not PGP/MIME, not integrity-protected, or not encrypted to this key), which is indexed only by its outer headers and counts as indexed. If `Email/changes` answers `cannotCalculateChanges` (a truncated change log, or a since-state the server no longer knows, for example after a restore), the app reconciles. It pages all mail again, refreshes the folders and flags of saved mail without downloading bodies again, and forgets mail the server no longer has. Until that pass completes, also across a restart, coverage does not count saved mail that the server has not confirmed (live proof of the server's answer to a since-state past the account's log: `packages/core/test/live/changes.live.ts`, passed on the local dev stack on 4 November 2026). Any other `Email/changes` error, for example `serverUnavailable`, does not reconcile: the app shows it as a sync error, keeps coverage as it was, and the next catch-up asks again from the saved state.
- Service worker: it precaches the app shell and never caches a response from the mail server. A new version goes live by itself; the browser looks for one at each load and when an installed app comes back into view. Once its shell is cached, open pages that an earlier worker served ask for the takeover at their next quiet moment (nothing sending or saving, no sign-in, key setup or sign-in code enrolment, no draft open or field being typed in while in view, and on a device not kept unlocked only once it is locked); without their answer the worker takes over at once (`skipWaiting`, then `clients.claim`). Every open Kasten page then locks, which saves an open draft and ends its key worker, and reloads at its next quiet moment. Until then it keeps running the previous version, with its files served from the previous shell, which activation keeps.
- Start-up: a start that finds no sealed refresh token in the local store shows Sign in before Unlock, so the passphrase is asked once, after the sign-in. Sign-out and an `invalid_grant` refresh remove that record, so its absence is the signed-out mark and no new plaintext is stored. When the server ends the sign-in while the app is locked, for example through `kasten lock`, only the next unlock finds out; that one time the app asks for the passphrase, then for sign-in, then for the passphrase again. A device kept unlocked opens with its saved unlock instead of the passphrase. A Lock button, sign-out, an `invalid_grant` refresh and a new key remove it; an update reload keeps it.
- Key setup: generate the key in the worker, protect it with the passphrase (S2K compatible with GnuPG), produce the printable recovery sheet (armored text plus QR codes), and import a sheet by paste, file or camera. The saved recovery file (built in `@kasten/core` as `RecoverySheet.file`: title, fingerprint, creation time, armored key and QR chunk lines) restores through **Choose the file**. The reader uses the armored block and the `KR1` lines, ignores the other lines, and refuses the file when the two halves belong to different keys. Upload the bundle, then set `encryptionAtRest`. The upload is the user key plus `operatorKeys`, sent as one `x:PublicKey`.
- MFA: the app enrols TOTP through `x:AccountPassword` while the client is first-party. Stalwart does not check the code at enrolment, so the app checks the user's first code locally before it saves the secret. After the lock, the operator turns codes on with `kasten user mfa new` and `kasten user mfa enrol`: for a person added later, or after `kasten user mfa reset` for a lost authenticator. The operator generates and briefly holds that key; `enrol` deletes the key file once the code works.
- After key setup and MFA enrolment, the operator runs `kasten lock`, which refuses an account without sign-in codes unless `--no-mfa` is given. The app then explains that key and MFA changes need the operator.
- Notifications: the device setting **Show sender and subject in notifications** is kept in the encrypted store, plus a plaintext copy of that value in the service worker's IndexedDB `kasten-sw`, because the service worker cannot read the encrypted store. `kasten-sw` also records whether this device's push subscription asks for `emailPush`. Neither value names a person or a message.

## `@kasten/core` modules

| Module   | Responsibility                                                                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jmap`   | Session, method calls, upload, download, EventSource; typed results; one error type that keeps the JMAP error type                                              |
| `auth`   | PKCE request, code exchange, refresh, logout; fetch-based, no storage of its own                                                                                |
| `crypto` | Key generation, unlock, export and import of the recovery sheet; decrypting stored PGP/MIME; encrypting a Sent copy; PKESK key-ID inspection without decryption |
| `mime`   | Parse with a maintained parser (postal-mime); build RFC 5322/MIME with correct RFC 2047 headers, CRLF and base64 attachments                                    |
| `mail`   | Mailboxes, threads, message lists, changes, identities, the send flow, outbox retry                                                                             |
| `safety` | `classifyStored(raw)`, a mirror of Stalwart's `is_encrypted` plus Kasten's own PGP/MIME acceptance rule; the key-set check; the plaintext Sent and draft check  |
| `search` | Index build, query and serialise; encryption is the caller's job                                                                                                |

Every module is written for Node 24 and current Safari, Chrome and Firefox. Its unit tests run in Node 24, and the web app's end-to-end tests run it in Chromium and WebKit; Firefox is not yet tested. The CLI runs the same decrypt and safety code as the app.

In the local dev stack only, `./kasten <command>` runs these in the `kasten-cli` image against the dev server, and adds `--config /kasten-dev/kasten.json` to the commands that take one. On the VPS, the operator runs them as root, from any directory: `kasten-cli <command> --config /etc/kasten/kasten.json`. `security-check`, `import-imap` and `read` run on the operator's computer instead, from a checkout, as `node cli/src/main.ts <command>`.

Dev-only settings, none of which production uses:

- `KASTEN_EXTRA_CA_FILE` makes the mail container trust the dev CA that signs the outbox certificate. Certificate checks stay strict.

The `admin` network is the tools network: only the CLI, `dev mail` and test containers use it. Mail from it skips the spam filter, so `.test` test mail reaches the Inbox. The admin key allows that network plus the default network's gateway `10.74.80.1`, which plays the part of the SSH tunnel.

The outbox has the host name `outbox.example.test`, because Stalwart refuses an EHLO that is not a domain name.

## Production host

- Fedora 45. `install.sh` runs only on the Fedora releases in its `SUPPORTED` list (44 and 45), and only while SELinux enforces the targeted policy with MCS. Podman, crun, conmon and passt come from Fedora's own packages. The mail and CLI containers use host networking, so Stalwart sees real client IPv4 and IPv6 addresses. The host's nftables `inet kasten` table is the firewall; Podman adds no rules, and Tailscale keeps its own tables.
- Firewall: inbound TCP 25 and 443 are public; SSH is open only over `tailscale0` and from the `--admin-ips` addresses of `install.sh`. Outbound allows DNS, NTP, HTTPS (443) and SES SMTP (587), and, for root only, HTTP to the provider's link-local metadata service (`169.254.169.254`, `fe80::a9fe:a9fe`), which cloud-init reads at every boot on Hetzner; outbound port 25 is dropped, and port 80 is otherwise closed, so dnf uses only HTTPS mirrors (`/etc/dnf/repos.override.d/50-kasten-https.repo`). `install.sh` renders the rules to `/etc/sysconfig/nftables.conf`, which Fedora's `nftables.service` loads. The drop-in `/etc/systemd/system/nftables.service.d/kasten.conf` keeps the rules loaded when the unit stops, and makes a reload replace only the `inet kasten` table. If firewalld is installed, `install.sh` disables and masks it.
- Rootless Podman. Podman runs as the host user `kasten` for every container: uid and gid 2600, home `/home/kasten`, a locked password and the shell `/usr/sbin/nologin`. Linger is on, so the user's manager, `user@2600.service`, starts at boot. It holds the containers' cgroups and the session bus that Podman uses. Container root is `kasten` itself, and container uid N is the Nth subordinate ID of `kasten`, from one range of at least 65536 IDs that `/etc/subuid` and `/etc/subgid` both give it. The mail server's uid 2525 is therefore `KASTEN_MAIL_UID` on the host: the first subordinate ID plus 2524, which is 526812 with Fedora's default range. `install.sh` writes it into `/etc/kasten/host.env`.
- Unprivileged ports start at 25 (`/etc/sysctl.d/50-kasten.conf`: `net.ipv4.ip_unprivileged_port_start = 25`, which also covers IPv6), so the server binds 25 and 443 without root. Ports below 25, such as SSH on 22, stay privileged. The mail containers keep `NET_BIND_SERVICE` only because Stalwart's binary carries it as a file capability, and exec fails without it. It counts only in the container's own user namespace, so it grants nothing on the host network.
- `kasten-podman <podman arguments>` runs Podman as `kasten`, for root. `setpriv` changes the user directly, and `env -i` gives Podman a clean environment: `PATH`, `HOME`, `XDG_RUNTIME_DIR=/run/user/2600`, the session bus, `TERM`, and `RESTIC_REPOSITORY`, `RESTIC_PASSWORD_FILE` and `KASTEN_BACKUP_ENV_FILE` when they are set. It opens no PAM session and starts no transient unit, because systemd refuses a transient unit while a shutdown is queued, and the stop at a reboot must still remove the mail container. It refuses to run until the manager `user@2600.service` has opened its session bus, `/run/user/2600/bus`. It refuses `run` and `create` unless `getenforce` prints `Enforcing`; only the local container test lifts this, with the file `/etc/kasten/test-without-selinux`.
- `/usr/local/lib/kasten/podman.sh` is the one definition of the containers. `kasten-mail-service`, `kasten-mail-run`, `kasten-cli` and `kasten-bootstrap` source it, and add each container's name, network, mounts and command. Every container has a read-only root file system and tmpfs where it needs one, and is removed when it stops. Images are loaded locally (`kasten-podman load`), and Podman names them `localhost/kasten-server:<version>` and `localhost/kasten-cli:<version>`, with the version from `KASTEN_VERSION`. Every run uses `--pull=never`; the VPS never pulls from a registry.

| Setting          | `MAIL_ARGS`: `kasten-mail`, `kasten-recovery`, `kasten-mail-run` | `CLI_ARGS`: `kasten-cli`, the bootstrap CLI                                   |
| ---------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Host user        | `KASTEN_MAIL_UID`, the image's uid 2525                          | `kasten` (`--user=0:0`)                                                       |
| Capabilities     | `--cap-drop=all --cap-add=net_bind_service`                      | `--cap-drop=all`                                                              |
| Privileges       | `--security-opt=no-new-privileges`                               | `--security-opt=no-new-privileges`                                            |
| Root file system | `--read-only --read-only-tmpfs=false`                            | `--read-only --read-only-tmpfs=false`                                         |
| tmpfs            | `/run/kasten`, 4 MiB, owned by the server's user                 | `/tmp`, 16 MiB                                                                |
| Memory           | `--memory=768m`                                                  | `--memory=384m`                                                               |
| PID 1            | The image's `tini`                                               | catatonit (`--init`), because the CLI's node process ignores SIGTERM as PID 1 |
| SELinux          | `--security-opt=label=level:s0:c525,c526`                        | `--security-opt=label=level:s0:c600,c601`                                     |
| Bind mounts      | `--volume=/var/lib/kasten/data:/var/lib/kasten:Z`                | Set by `kasten-cli` and `kasten-bootstrap`                                    |

- The encrypted volume is a file-backed LUKS2 container, `/var/lib/kasten.luks`. `kasten-unlock.service` unlocks it with Clevis through Tang (or `kasten-unlock-passphrase` with the recovery passphrase) and mounts it at `/var/lib/kasten`. `kasten-unlock-passphrase` then starts `kasten.service`, but only once the first boot is done. While Tang is unreachable, `kasten-unlock.service` retries every minute, and it starts `kasten.service` once the volume is mounted (not yet tested on a real VPS). The containers see the mount because systemd mounts `/` as shared: the mount at unlock reaches Podman's mount namespace, and the unmount at a lock removes it there too. `install.sh` labels the new file system once with `restorecon` after `mkfs`. Each container's `:Z` mount then labels its directory with that container's MCS level. The directories:

| Path                        | Owner and mode                                                                         | MCS level            | Mounted into                                                          |
| --------------------------- | -------------------------------------------------------------------------------------- | -------------------- | --------------------------------------------------------------------- |
| `/var/lib/kasten`           | root, 0755; immutable (`chattr +i`) while unmounted                                    | No container level   | No container                                                          |
| `/var/lib/kasten/data`      | `KASTEN_MAIL_UID`, 0700                                                                | `s0:c525,c526`, mail | The mail containers, as `/var/lib/kasten`                             |
| `/var/lib/kasten/cli`       | `kasten:kasten`, 0700; every file in it `kasten:kasten`, without group or other access | `s0:c600,c601`, CLI  | `kasten-cli`, read-only as `/etc/kasten`; the bootstrap CLI, writable |
| `/var/lib/kasten/cli/state` | `kasten:kasten`, 0700                                                                  | `s0:c600,c601`, CLI  | `kasten-cli`, writable as `/etc/kasten/state`                         |
| `/var/lib/kasten/secrets`   | root, 0700; `backup.env` 0600                                                          | No container level   | No container                                                          |

- `cli/` holds `kasten.json` and the files it names, and `cli/state/` holds the CLI's state. `data/secrets/` holds the recovery login, and the restic password file and the backend settings, which are owned by `KASTEN_MAIL_UID` with mode 0600. `secrets/backup.env` names those two files for `kasten-backup.service`.
- `/opt/kasten/.env` sets `KASTEN_VERSION`, `KASTEN_VOLUME_ID`, `STALWART_PUBLIC_URL` (`https://<mailApiHostname>`). It is not secret: `kasten-mail` and each `kasten-mail-run` container read it with `--env-file`, so every line reaches them.
- systemd: `kasten.service` (oneshot, `RemainAfterExit=yes`) runs the mail server. Its first `ExecStart=` runs `kasten-mail-service start`, which runs `kasten-podman run --detach --replace --name kasten-mail --restart=on-failure --stop-timeout=60 --network=host --env-file=/opt/kasten/.env` with `MAIL_ARGS` and the server image; `kasten-podman` runs it as Podman for `kasten`. `kasten-mail-service start` becomes that process (`exec`): rootless Podman moves itself out of the unit's cgroup, so systemd must signal it by its process id. The second `ExecStart=` runs `kasten-mail-service wait`, which waits up to 240 seconds for the container's health check; an exit or a failed check ends the wait early. `ExecStopPost=` runs `kasten-mail-service stop`, which stops the container (up to 60 seconds), logs `kasten-mail stopped: exit status N` and removes it. It also runs after a start that failed or was cancelled, for example by a lock during the health wait, so no container keeps the volume busy. Podman's restart policy (`on-failure`) starts the server again after a crash; a stop through Podman is final. Podman runs the first health check 30 seconds after the start, so a start takes about 30 to 35 seconds. The containers run in the cgroup of `user@2600.service`, not of the unit that started them; their memory limits still apply. journald therefore files a container's output under `user@2600.service`, so `kasten-backup.service`, `kasten-check.service` and `kasten-probe.service` set `SyslogIdentifier=` to their own names, and `journalctl -t kasten-backup`, `-t kasten-check` and `-t kasten-probe` show their reports. Do not run `kasten-mail-service` by hand: `systemctl start kasten.service` first checks the unlock, the mount and the finished first boot.
- Ordering and lock: `kasten.service` has `Requires=kasten-unlock.service user@2600.service`, `After=kasten-unlock.service var-lib-kasten.mount user@2600.service` and `PartOf=user@2600.service`, so a restart of the user manager restarts it too. It starts only after `kasten-unlock.service` has unlocked and mounted the volume, and only after the first boot: it asserts that `/var/lib/kasten` is a mount point, that `data/stalwart/stalwart.sqlite` exists and that `.kasten-bootstrap-incomplete` does not. A start before then would be Stalwart's first normal start, with a network. Because it is ordered after `user@2600.service`, it stops first at a shutdown, while Podman still works, so the mail container is gone before the volume locks. `systemctl stop kasten.service kasten-unlock.service` locks the volume: it stops and removes the mail container, then unmounts and closes the volume.

- `kasten-mail-exec` and `kasten-mail-run` pass `RESTIC_REPOSITORY`, `RESTIC_PASSWORD_FILE` and `KASTEN_BACKUP_ENV_FILE` into the container when they are set, and nothing else from the caller's environment.
- First boot: `kasten-bootstrap` runs once, after `kasten-mail-run init`. It starts `kasten-recovery`, a mail container that runs `kasten-server recovery` with `--network=none`, and waits up to 300 seconds for its health check. It then runs `kasten setup --bootstrap` in a CLI container with `--network=container:kasten-recovery`, so it shares only the recovery container's loopback. For that run, `/var/lib/kasten/cli` is writable. `kasten-bootstrap` copies the recovery login to `/var/lib/kasten/cli/recovery-admin` (owner `kasten`, mode 0600) only for that run, because the CLI cannot read the original, which belongs to the server's user. Bootstrap writes the admin API key to the file that `admin.apiKeyFile` names, for example `/var/lib/kasten/cli/admin-api-key`. On a volume without a database, `kasten-bootstrap` first creates `/var/lib/kasten/.kasten-bootstrap-incomplete`, and deletes it when setup has finished. At the end it removes the copy and `kasten-recovery`, also after Ctrl-C, a dropped SSH session or SIGTERM.
- `kasten-backup.timer` runs `kasten-backup.service` nightly at 03:15 (random delay up to 30 minutes). That unit runs `kasten-mail-exec backup`, which is `kasten-server backup` in the mail container, with the settings in `/var/lib/kasten/secrets/backup.env`. Generic check/probe unit files remain available but are not enabled by the installer.
- No plaintext reaches the unencrypted disk:
  - Podman's transient store (`transient_store = true` in `/home/kasten/.config/containers/storage.conf`) keeps its database and every container's state in `/run/user/2600/containers`, in RAM. That state includes the environment of every exec and the arguments of every run. The images stay on the root disk, in `/home/kasten/.local/share/containers/storage`, and survive a reboot.
  - journald keeps the logs in RAM only (`/etc/systemd/journald.conf.d/kasten.conf`, 32 MiB) and forwards nothing to a syslog daemon. `install.sh` refuses to run beside `rsyslog` or `syslog-ng`. `/etc/containers/containers.conf.d/50-kasten.conf` makes `journald` Podman's default log driver, and turns off the journal event for each health check (`healthcheck_events = false`).
  - No disk swap: zram swap in RAM instead (`/etc/systemd/zram-generator.conf`), and the `.swap` unit of each disk swap is masked.
  - No core dumps (`/etc/systemd/coredump.conf.d/kasten.conf`: `Storage=none`).
  - `auditd.service` is masked, because it would write the audit log to the disk. The kernel's audit messages still reach the journal in RAM.
- `systemd-oomd.service` and `systemd-oomd.socket` are masked, because systemd-oomd would kill the mail container's cgroup under memory pressure. The containers' memory limits and the kernel's OOM killer stay.
- Updates: `dnf5-automatic.timer` applies all Fedora updates every morning, unattended (`/etc/dnf/automatic.conf`: `upgrade_type = default`, `apply_updates = yes`, `reboot = never`). It never reboots; `dnf5 needs-restarting` says when a reboot is due. A running container keeps the old Podman and crun until its next start. `dnf-makecache.timer` is masked, because dnf5-automatic refreshes the metadata once a day.
- Images reach the VPS through `docker save "kasten-server:$v" "kasten-cli:$v" | ssh root@<vps> kasten-podman load`, built with Docker on your computer for `linux/amd64` and tagged `kasten-server:<version>` and `kasten-cli:<version>`.
