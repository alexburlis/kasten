# Stalwart v1.0.1: what Kasten relies on

This page is the reference for the parts of Kasten that talk to Stalwart: `kasten setup`, the other CLI commands and the web app. It records how Stalwart v1.0.1 actually behaves, with evidence.

- **Reproduced** means an agent ran it against Stalwart v1.0.1 in Docker on 3 or 4 November 2026 and saw the result.
- **Inspected** means an agent read the v1.0.1 source (`git describe` = `v1.0.1`); `file:line` points into it.

The research server was the official image `stalwartlabs/stalwart@sha256:b9da4df8b4efc06bc926dd6e990bdeb0ad7b9261a7c3893d74b0461a00bb389b` (arm64). It is built with the same feature flags as the release tarballs (`sqlite postgres mysql rocks s3 redis azure nats enterprise`, `.github/workflows/ci.yml:361,406,462`). It used SQLite, as Kasten does. Everything below that needs the public internet (Let's Encrypt, real Web Push, SES) was not tested; each such item says so.

## 1. Bootstrap and the admin credential

**Answer.** Bootstrap needs one recovery-mode run. In it, the recovery admin creates a key-only admin account and an IP-restricted `x:ApiKey` for that account. Normal runtime then uses only that key; `STALWART_RECOVERY_ADMIN` is never set.

### Recovery mode

| Variable                              | Effect                                                                                                                                                                              | Evidence                                                                                                                                                         |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `STALWART_RECOVERY_MODE=1`            | One plain-HTTP listener `http-recovery` on `[::]:<port>`. No SMTP/IMAP. No task manager, queue or push. Rate limits, fail2ban and `allowedEndpoints` are off; CORS is forced to `*` | Reproduced (log `Server started in recovery mode`); inspected `crates/common/src/config/server/listener.rs:56-90`, `crates/common/src/config/network.rs:449-499` |
| `STALWART_RECOVERY_MODE_PORT`         | Port of that listener; default 8080                                                                                                                                                 | Inspected `listener.rs:38-45`                                                                                                                                    |
| `STALWART_RECOVERY_ADMIN=user:secret` | A superuser login, `Permissions::all()` including `impersonate`                                                                                                                     | Inspected `crates/common/src/auth/access_token.rs:988-999`                                                                                                       |

**`STALWART_RECOVERY_ADMIN` also works in normal mode** while the variable is set: `authenticate_basic` checks it first, with no recovery-mode guard (inspected `crates/common/src/auth/authentication.rs:133`). Reproduced: without the variable, the same login gets HTTP 401 in normal mode. Kasten sets it only for `kasten-server recovery`. `kasten-server serve` refuses to start while any `STALWART_RECOVERY_*` variable is set (inspected `server/bin/kasten-server`, `cmd_serve`).

First start in recovery mode also inserts an enabled `x:Application` (the web UI) and fetches it from GitHub (reproduced: log `Application resource updated ... webui.zip`). Kasten runs that start without a network, so the fetch fails and nothing is downloaded. See [section 6](#6-no-web-admin-ui-no-management-with-user-credentials) and [section 13](#13-first-boot-without-downloads).

## 2. OAuth sign-in for the web app

**Answer.** Stalwart's own login page and an admin-created client give a standard authorization-code flow with PKCE S256 for a public client. A scripted Node sign-in that ends with a JMAP call passes (`cli/test/integration/oauth.test.ts`, run by `cli/test/integration/stalwart-docker.sh`).

### Discovery

`GET /.well-known/oauth-authorization-server` and `GET /.well-known/openid-configuration` (reproduced):

| Field                                                    | Value                                                                                                                                        |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `issuer`                                                 | `STALWART_PUBLIC_URL`, else `https://<hostname>`                                                                                             |
| `authorization_endpoint`                                 | `{issuer}/login` (an HTML page; there is no `/authorize`)                                                                                    |
| `token_endpoint`                                         | `{issuer}/auth/token`                                                                                                                        |
| `revocation_endpoint`                                    | `{issuer}/auth/revoke`                                                                                                                       |
| `end_session_endpoint`                                   | `{issuer}/auth/logout`                                                                                                                       |
| `registration_endpoint`, `device_authorization_endpoint` | `{issuer}/auth/register`, `{issuer}/auth/device` (always advertised; refused by Kasten, [section 4](#4-refusing-public-client-registration)) |
| `introspection_endpoint`                                 | `{issuer}/auth/introspect` (RFC 8414 document only)                                                                                          |
| `code_challenge_methods_supported`                       | `["S256"]`                                                                                                                                   |
| `scopes_supported`                                       | `openid`, `offline_access`, `urn:ietf:params:oauth:scope:mail`, `...:contacts`, `...:calendars`, `...:files`                                 |
| `token_endpoint_auth_methods_supported`                  | `none`, `client_secret_post`, `client_secret_basic`                                                                                          |
| `client_id_metadata_document_supported`                  | `true`, hard-coded, although the policy `x:OidcProvider.clientMetadataDocuments` defaults to `"disabled"`                                    |

### The client

`x:OAuthClient/set create` (reproduced):

```json
{
  "clientId": "kasten-web",
  "description": "Kasten web app",
  "redirectUris": { "http://localhost:7480/oauth/callback": true },
  "scopes": { "mail": true },
  "grantTypes": { "authorizationCode": true, "refreshToken": true },
  "firstParty": true
}
```

- `redirect_uri` must equal a registered URI exactly. Only `127.0.0.1` and `[::1]` get port-agnostic loopback matching. Admin-created clients may use `http://localhost:...` (inspected `crates/common/src/auth/oauth/client.rs:387-393`).
- No `secret` makes it a public client; PKCE is then required (inspected `crates/http/src/auth/oauth/authorize.rs:236-262`).
- `firstParty` decides what the token may do; see [section 3](#3-scopes-and-what-an-app-token-can-do).

### The flow, as the login page does it

1. The app sends the browser to `GET {issuer}/login?response_type=code&client_id=...&redirect_uri=...&scope=...&state=...&code_challenge=<S256>&code_challenge_method=S256`. **`state` is mandatory.** `plain` PKCE is refused.
2. The page calls `GET /api/auth/client?<same query>` with `Accept: application/json`. Success: `{"name","logo","clientHost","redirectHost","scopes":[labels],"verified","consentRequired"}`. Error: `{"error","description","redirect","location"}`.
3. The page posts `POST /api/auth`, `Content-Type: application/json`: `{"type": "authCode", "accountName": "<email>", "accountSecret": "<password>", "query": "<the query string, without ?>"}`.
4. The reply is HTTP 200 with a `type`:
   - `mfaRequired`: post the same body again with `"mfaToken": "123456"`;
   - `consentRequired` with `token`: post `{"type": "authConsent", "token": "...", "query": "...", "consent": true}`. Consent is asked only while the account has no grant for this client (reproduced: a second sign-in skipped it);
   - `authenticated` with `location`: `<redirect_uri>?code=...&state=...&iss=<issuer>`;
   - `failure`, `invalid`, `expired`, `redirect`.
5. The app exchanges the code: `POST /auth/token`, `application/x-www-form-urlencoded`, fields `grant_type=authorization_code`, `code`, `redirect_uri`, `client_id`, `code_verifier`. A wrong verifier gets HTTP 400 `{"error": "invalid_grant"}` and does not use up the code.

Reproduced end to end; the login page source is `resources/html-templates/login.html:502-505, 726-828`. The server keeps no session or cookie, so every authorization asks for the password, and `prompt=none` or hidden-iframe renewal is impossible: the app depends on refresh tokens.

### Tokens

The token response (reproduced):

```json
{
  "access_token": "...",
  "token_type": "bearer",
  "expires_in": 3600,
  "refresh_token": "...",
  "scope": "openid offline_access urn:ietf:params:oauth:scope:mail",
  "username": "you@kasten.test",
  "id_token": "..."
}
```

| Setting (`x:OidcProvider`) | Default                                                       | Meaning                                                 |
| -------------------------- | ------------------------------------------------------------- | ------------------------------------------------------- |
| `accessTokenExpiry`        | 3600000 (1 h), minimum 10 min                                 | Access token lifetime                                   |
| `refreshTokenExpiry`       | 2592000000 (30 days), minimum 1 day                           | How long an app may stay unused before it is signed out |
| `authCodeExpiry`           | 600000                                                        | Authorization code lifetime                             |
| `encryptionKey`            | Random at first start (`{"@type": "Value", "secret": "..."}`) | Encrypts tokens and dynamic client ids                  |

- **Rotation:** every refresh returns a new refresh token. Re-presenting the immediately previous one, while the newest is unused, still works (reproduced). Presenting an older one revokes the whole grant ("Superseded refresh token reused", inspected `crates/common/src/auth/oauth/grant.rs:415-446`; live proof: `tests/integration/oauth.test.ts`, passed on the local dev stack on 4 November 2026). The exact rule (inspected, same lines): a token of the current generation is a Retry while the newest is unused, otherwise a Rotate. A token one generation ahead while a rotation is pending rotates. Any older token is a Replay, which deletes the grant and stops its access tokens (HTTP 401).
- A refresh after the client's kind changed (for example `firstParty` turned off) fails with `invalid_grant` **and deletes the grant** (reproduced; inspected `crates/http/src/auth/oauth/token.rs:456-467`).
- `refresh_token` is issued whether or not `offline_access` is requested; `grantTypes.refreshToken` is the only gate.
- Access tokens are opaque and bound to an `x:OAuthGrant`. Removing the grant stops its access tokens at once (reproduced: HTTP 401).

| Action                                                                          | Effect                                                                                                                                | Evidence                                                            |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `POST /auth/revoke` with `token=<refresh or access token>&client_id=kasten-web` | Deletes the whole grant: refresh fails with `invalid_grant`, the access token gets 401 at once. Returns 200 even for an unknown token | Reproduced                                                          |
| `GET /auth/logout`                                                              | A static "You have been signed out" page. It revokes nothing                                                                          | Reproduced; inspected `crates/http/src/auth/oauth/logout.rs:63-104` |

## 3. Scopes, and what an app token can do

**Answer.** v1.0.1 has no settings scope. A non-first-party client's token can use mail, but **no** `x:*` object, so it cannot change keys. A first-party client's token has the account's full own permissions. `kasten lock` therefore turns `firstParty` off and removes the client's grants.

| Fact                                                                                                                                                                                          | Evidence                                                                        |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Scope strings: `openid`, `offline_access`, `urn:ietf:params:oauth:scope:mail`, `...:contacts`, `...:calendars`, `...:files`. Client `scopes` values: `mail`, `contacts`, `calendars`, `files` | Inspected `crates/common/src/auth/oauth/mod.rs:26-47`; schema enum `OAuthScope` |
| The app should request `openid offline_access urn:ietf:params:oauth:scope:mail`. Any unknown or unlisted scope fails the whole request with `invalid_scope` (including `email`, `profile`)    | Inspected `authorize.rs:331-349`; reproduced for an unlisted scope              |
| No scope maps to any `sys*` permission, so `x:AccountSettings/*`, `x:PublicKey/*`, `x:AccountPassword/*` and `x:AppPassword/*` are `forbidden` for a non-first-party token                    | Inspected `crates/common/src/auth/oauth/scope.rs:204-432`; reproduced           |
| `firstParty: true` ignores scopes: the token carries the account's full permissions (still no admin objects)                                                                                  | Inspected `scope.rs:463-476`; reproduced                                        |
| Changing a client's `firstParty` does not change tokens already issued. Their refresh then fails, but their access tokens work until the grant is removed                                     | Reproduced                                                                      |

## 4. Refusing public client registration

**Answer.** `POST /auth/register` needs no sign-in and creates a stateless client id. Kasten refuses it, device sign-in and the built-in `/login` page through `x:Http.allowedEndpoints`. A wrong-typed rule fails open, so `kasten setup` reads the rule back and the live tests check the 403 (`cli/test/integration/setup.test.ts`, `tests/integration/security.test.ts`).

| Fact                                                                                                                                                                                                                                                                    | Evidence                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Public registration accepts loopback (`http://127.0.0.1/...`, `http://[::1]/...`) and private-use-scheme redirect URIs; it returns HTTP 201 and `client_id` `swc1.<encrypted>`. Nothing is stored; the id never expires                                                 | Reproduced; inspected `crates/http/src/auth/oauth/registration.rs:98-147`                                                                                                                                                                                                |
| Ids issued before the refusal keep working (`/api/auth/client` answered for `openid`) **until `x:OidcProvider.encryptionKey` changes**; then "Unknown client id". Changing the key also invalidates every refresh token; access tokens survive                          | Reproduced                                                                                                                                                                                                                                                               |
| Device sign-in exists (`POST /auth/device`, page `/device`) but only for a stored client whose `grantTypes` include `deviceCode`                                                                                                                                        | Reproduced `unauthorized_client`; inspected `crates/common/src/auth/oauth/client.rs:421-427`                                                                                                                                                                             |
| `allowedEndpoints` runs first for every HTTP request, before routing and authentication. The result must be an HTTP status; only `200` allows                                                                                                                           | Inspected `crates/http/src/request.rs:107-117`                                                                                                                                                                                                                           |
| **Loopback clients bypass a refusal**, so test from a non-loopback address                                                                                                                                                                                              | Inspected `request.rs:113`                                                                                                                                                                                                                                               |

## 5. CORS for the app's origin

**Answer.** Exact-origin CORS works through `x:Http.responseHeaders`. The permissive `*` switch is not needed.

Kasten writes, with `usePermissiveCors: false`:

```json
{
  "Access-Control-Allow-Origin": "http://localhost:7480",
  "Access-Control-Allow-Methods": "GET, POST, OPTIONS",
  "Access-Control-Allow-Headers": "Authorization, Content-Type, Accept",
  "Access-Control-Max-Age": "600"
}
```

Reproduced with `Origin: http://localhost:7480` (a research script, not kept; `cli/test/integration/setup.test.ts` and `tests/integration/security.test.ts` repeat the preflight checks):

| Request                                                                                                                                                                                        | Status   | CORS headers                         |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------ |
| `OPTIONS` on `/jmap/`, `/jmap/session`, `/jmap/upload/c/`, `/jmap/download/c/x/y`, `/jmap/eventsource/`, `/auth/token`, `/auth/revoke`, `/api/auth`, `/.well-known/oauth-authorization-server` | 204      | all four, exact origin               |
| `POST /jmap/` (200), without auth (401), bad JSON (400)                                                                                                                                        | as shown | all four                             |
| `POST /jmap/upload/c/` 200, `GET /jmap/download/...` 404, `GET /jmap/eventsource/` 200                                                                                                         | as shown | all four                             |
| `POST /auth/token` with a bad grant (400), `POST /auth/register` (403)                                                                                                                         | as shown | all four                             |
| Before configuration                                                                                                                                                                           | 204      | none, except `*` on `/.well-known/*` |

Limits (inspected `crates/common/src/config/network.rs:424-472`, `crates/http/src/request.rs:928-1031`):

- The headers are static. Stalwart cannot reflect `Origin` or allow two origins.
- A request from another origin therefore gets the same `Access-Control-Allow-Origin: <app origin>`, never its own origin and never `*`. The browser compares that header with its own origin and refuses the response. A check must assert "never the caller's origin, never `*`", not "no allow header" (`tests/integration/security.test.ts`, "never allows another origin").
- `usePermissiveCors: true` appends `*` after the custom headers and wins. Keep it false.
- Two early responses carry no CORS headers: 400 for a malformed `X-Forwarded-For`, and 403 for a blocked IP.
- An invalid header name passes `x:Http/set` but makes `ReloadSettings` fail; at startup it drops all custom headers.
- **Browsers:** native `EventSource` cannot send `Authorization`, and Stalwart ignores `?access_token=` (reproduced: 401). The app must read `/jmap/eventsource/` with `fetch()` and a stream reader. Downloads also need `fetch()` with the header, then a blob URL.

The fallback, if a real Safari preflight ever fails, is `usePermissiveCors: true` with bearer tokens and no cookies; the docs must then not claim origin restriction. No such failure was seen. The web app's browser tests (`web/e2e/`) run in Playwright's Chromium and WebKit, with the app on `http://localhost:7480` and the API on `http://localhost:7481`, so their JMAP calls are cross-origin requests with a preflight. Safari on a real iPhone is not yet tested.

## 9. Admin writes of another account's keys

**Answer.** Yes. An admin key holds `impersonate`, so the admin can create `x:PublicKey` and set `x:AccountSettings.encryptionAtRest` in any user's account by passing `accountId`.

```json
[
  [
    "x:PublicKey/set",
    {
      "accountId": "<user>",
      "create": { "k": { "description": "key bundle", "key": "<armored public keys>" } }
    },
    "p"
  ],
  [
    "x:AccountSettings/set",
    {
      "accountId": "<user>",
      "update": {
        "singleton": {
          "encryptionAtRest": {
            "@type": "Aes256",
            "publicKey": "#k",
            "encryptOnAppend": true,
            "allowSpamTraining": false
          }
        }
      }
    },
    "s"
  ]
]
```

Reproduced: `created`, `updated`, and the readback shows `{"@type": "Aes256", "publicKey": "<id>", "encryptOnAppend": true, "allowSpamTraining": false}`. One `x:PublicKey` may hold several armored keys in one string (reproduced with two). `kasten keys set` stores the user's key and the operator keys this way, as one `x:PublicKey` (inspected `cli/src/keys.ts`). `x:PublicKey` also has `expiresAt`, `emailAddresses` and an immutable `accountId`. The user can do the same in their own account with a password, an `Inherit` app password or a first-party token.

## 13. First boot without downloads

## What `kasten setup` writes

`kasten setup` applies this state, then reads every value back and fails if any differs. Sizes, lifetimes and rates come from `limits` in `kasten.json`; the table shows their defaults. The development values were run live; the production-only values (443 listener, admin listener on 127.0.0.1, STARTTLS on 25, ACME, HSTS) come from the same code path but were not run against a real server. A second run changes nothing (`cli/test/integration/setup.test.ts`, "changes nothing on a second run, and still reloads what an earlier run stored", which `cli/test/integration/stalwart-docker.sh` runs). Every normal run sends `ReloadSettings` before its readback, even when it changed nothing, because an earlier run may have stored a setting and failed before its reload. Before its first write of a restart-only object, a normal run records the object in `setup-restart.json` in the state directory. A successful run prints `Restart Stalwart to apply: ...` for every object recorded there, then clears the file; a run that fails after such a write leaves it for the next run (inspected `cli/src/setup/setup.ts`; that test's check of the reload passed on 5 November 2026). The number of checks depends on `kasten.json`. With the dev stack's `kasten.json` (one domain, three users, the IMAP import listener), `./kasten dev up` on a fresh volume on 4 November 2026 gave: bootstrap 30 changes and 36 readback checks; first normal run 7 changes and 46 checks; a further `kasten setup` 0 changes and 46 checks.

### The outbound cap

Only an inbound RCPT-stage throttle counts recipients, and JMAP submission runs through it. Reproduced with the cap set to 2: one `EmailSubmission` to three external recipients gave `one@`, `two@` `250 2.1.5 Queued` and `three@` `452 4.4.5 Rate limit exceeded, try again later.` in `deliveryStatus`. The submission is still created; refused recipients are not retried. The window is fixed and resets at 00:00 UTC. `x:MtaOutboundThrottle` cannot count recipients and delays rather than refuses (inspected `crates/common/src/config/smtp/queue.rs:478-565`, `crates/smtp/src/inbound/rcpt.rs:253, 342-345`). The cap does not limit stolen SES credentials used outside Stalwart.

### Upload limits

One send uploads the message, then its encrypted Sent copy, which is larger. `kasten setup` therefore sets `x:Jmap.maxUploadSize` to 1.4 times `limits.sendMessageBytes`: the armored Sent copy is about 1.378 times the message, plus its key packets and headers (`maxSentCopyBytes` in `packages/core/src/mail/send.ts`). It sets `uploadQuota` to the send limit plus `maxUploadSize`, so the message and its copy fit in one `uploadTtl` window. With the default send limit of 38000000 bytes, that gives 53200000 and 91200000 (inspected `cli/src/setup/specs.ts`; live proof: `cli/test/integration/setup.test.ts` and `packages/core/test/live/send.live.ts`, "stores the Sent copy of a message at the 38 MB send limit in one pass", both passed on 5 November 2026).

## Findings that change other parts

- **Bootstrap is one recovery run, then a normal start, then `kasten setup`.** The API key can be created in recovery mode. Some settings must wait for the normal start: `x:Jmap` (Web Push key), routes and throttles. In production the ACME provider must wait too, because creating it needs the network.
- **`STALWART_PUBLIC_URL` must be set** in every normal-mode run: `http://localhost:7481` in dev, `https://mail.example.com` in production. Without it, the issuer and session URLs use `https://<STALWART_HOSTNAME>`, which is the MX name.
- **The web app** must use `fetch()` streaming for EventSource and downloads, check a TOTP code locally before enrolling, request exactly `openid offline_access urn:ietf:params:oauth:scope:mail`, and always send `state`.
- **`kasten lock --account <email>`** checks the account's key bundle, sets `firstParty: false` on the client, destroys that client's `x:OAuthGrant`s in that account and pins the fingerprints. It then signs in as the probe account through the locked client and requires `forbidden` on `x:PublicKey/set`, `x:AccountSettings/set` and `x:AppPassword/set`. A new key set must hold the user key whose fingerprint `--user-fingerprint` gives, from the owner's recovery sheet. The account must have sign-in codes, unless `--no-mfa` is passed. The lock pins nothing while the account has app passwords or API keys other than Kasten's reader and import passwords; `--revoke-others` destroys them (inspected `cli/src/lock.ts`). Run it once per account. Re-running `kasten setup` never undoes it. Setup never changes `firstParty` on an existing client. Once `lock.json` pins an account, or an `x:OAuthClient` reads back with `firstParty: false`, setup creates any client it must create with `firstParty: false`: for a changed `webApp.oauthClientId`, or when the client is gone. Before any change it records that client in `setup-lock-due.json` in the state directory; a successful run then prints that `kasten lock` must run again for every account and clears the file (inspected `cli/src/setup/specs.ts`, `cli/src/setup/setup.ts`; unit test `cli/test/unit/setup.test.ts`). `kasten check` holds every Sent copy to the strict rule unless an operator lists it, because `Email/import` and APPEND both keep a `receivedAt` that the storing client or import source chooses (inspected `packages/core/src/safety/check.ts`). The one exception, `earlierKeySet` after a key change, trusts that date for a Sent copy too; `docs/security.md` says why. After a key change, the lock keeps the old pin as an earlier set, dated by the new `x:PublicKey`'s `createdAt`: the server's clock, in whole seconds like `receivedAt` (reproduced: `tests/integration/cli-keys-lock.test.ts`).
- **Credential permissions do not cover HTTP blob routes:** any credential of an account can download its blobs by id and upload temporary blobs.
- **Registration refusal** fails open on a wrong-typed rule and is bypassed from loopback. So `kasten security-check` must run from a non-loopback address; it reports FAIL for registration when its URL is a loopback address (`tests/integration/cli-security-check.test.ts`). Rotating `x:OidcProvider.encryptionKey` is the only way to invalidate `swc1.` client ids already issued.
- **App passwords with `Inherit`** can change the key set. Anything other than the user's own mail client gets a `Replace` list: `kasten reader create` for the reader, `kasten app-password create --purpose import` for the import ([section 16](#16-imap-import)).
