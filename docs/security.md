# Security model

This page says what Kasten protects, what it does not protect, and when you must stop and decide. Read it before you move real mail in.

## The parts and who can read what

| Part                         | Holds                                                                                                                                                                                         | Can read your stored mail?                                                                                                                                       |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Your devices, in the web app | Your private key, wrapped by its recovery code (or a passphrase you chose); an encrypted local cache                                                                                          | Yes, after you unlock the app, or at any time on a device you keep unlocked                                                                                      |
| Your passkeys                | Nothing of the key; each one, after your face, fingerprint or PIN, gives the app the secret that opens its passkey record                                                                     | Yes, together with a sign-in to your account or a device that holds the passkey records                                                                          |
| The recovery sheet           | An encrypted copy of your private key and, for a key Kasten gave a recovery code, that code                                                                                                   | With the recovery code on it, yes, by itself. Without one, only together with your passphrase                                                                    |
| The mail server (VPS)        | Your public key bundle; the mail store on a LUKS disk; your private key encrypted with its recovery code or passphrase, and that code encrypted to each passkey, in the **Kasten key** folder | No, except new mail as it arrives and the exceptions listed below. With a guessed passphrase you chose, yes: see [The key on the server](#the-key-on-the-server) |
| The app host                 | The static web app files                                                                                                                                                                      | Not directly, but it can change the app and so steal your key                                                                                                    |
| The DNS account              | The record that points the app name at the app host                                                                                                                                           | Not directly, but it can point the app name elsewhere or turn on a proxy, and so change the app                                                                  |
| Amazon SES                   | Each outgoing message while it sends                                                                                                                                                          | It sees every message you send                                                                                                                                   |
| The backup bucket            | restic snapshots, encrypted with the restic password                                                                                                                                          | No. With the restic password, someone can read the metadata and the [messages stored as they are](#messages-the-server-stores-as-they-are)                       |
| The operator key             | A second private key, kept in your password manager. `kasten setup` requires its public key                                                                                                   | Yes: every stored message is also encrypted to it                                                                                                                |

## What Kasten protects

- **Stored message content.** Stalwart encrypts each incoming message to your OpenPGP key bundle before it stores it. The server holds only the public keys. A copy of the mail store, or a backup with its restic password, does not reveal message bodies or attachments without a private key. The exceptions are the [messages stored as they are](#messages-the-server-stores-as-they-are).
- **Mail you send.** The app submits each message and, in the same request, asks the server to delete its readable copy once the submission succeeds. The app then stores its own Sent copy, encrypted to your key bundle. `kasten check` reports any readable Sent copy that is left.
- **Drafts.** Drafts stay on your device, in the encrypted local store. `kasten check` reports any readable draft on the server that is older than one hour.
- **Your private key.** The key is created in the app and never leaves your devices unencrypted. The mail server keeps it only encrypted with its recovery code (or the passphrase you chose), and keeps that code encrypted to each of your passkeys, so that a new device needs nothing but a sign-in and a passkey: see [The key on the server](#the-key-on-the-server).
- **The local cache.** The app encrypts every record it keeps on the device, including the search index, with AES-GCM under a random data key. A key derived from your passphrase (PBKDF2-SHA-256) wraps that data key. A few things stay readable on purpose: the store's schema version, its record counts and the wrapped key; a push verification code that arrived while no Kasten window was open, which the app accepts for 10 minutes and which is removed when the app reads it or, once expired, at the next push or app start; remote images in the browser's cache after you press **Show**; the setting that decides whether notifications show the sender and subject; and the notifications themselves. On a device you keep unlocked, the app also stores your passphrase, encrypted with a device key that the browser keeps and that script can use but not read. A device whose key has passkeys keeps their records, each the passphrase encrypted to one passkey, so it can ask a passkey while locked and offline. [web/README.md](../web/README.md#where-plaintext-lives) lists every place.
- **Disk residue.** The mail data, temporary uploads, Stalwart's and the CLI's configuration and the server credentials sit on a LUKS-encrypted volume. Logs stay in RAM, and every container has a read-only root file system. Podman keeps its container and exec state in RAM too (a transient store), and core dumps are not stored. A copy of the powered-off disk shows the operating system and the Podman images, but only ciphertext for the volume.

## What Kasten does not protect

- **Mail in transit.** Ordinary email is readable while the server receives it. The sender's provider, and SES for mail you send, also see it. Kasten protects stored mail, not mail in transit.
- **Headers and metadata.** Sender, recipients, subject, dates, sizes, flags and folder names stay readable on the running server and inside decrypted backups. The server's log, in RAM, also holds envelope addresses, client IP addresses and Message-IDs.
- **A running server that someone controls.** Someone with root on the running server can read new mail as it arrives. The server must decrypt the disk to work, so LUKS does not help against this attacker.
- **The app host.** Someone who controls where the app is served can change it and steal your key the next time you open the app. They can then read your old mail too. A new app version goes live by itself: an open Kasten page reloads into it when nothing is in progress there, and the worker keeps the previous version's files for a page that has not reloaded yet. That rule keeps pages consistent; it does not protect you from a changed app host.
- **Your devices.** Malware on an unlocked device can read what the app shows. A lost device stays protected only by the device's own lock and by what unlocks the app: your recovery code or passphrase, or a passkey, whose provider asks for your face, fingerprint or PIN. **Keep unlocked on this device** is ticked by default on the unlock screen. On a device where it is on, only the device's own lock protects it: the app opens there without the passphrase, also offline, and so does a copy of the browser's profile taken from the device's disk. Ending that device's sign-in on the server ends the saved unlock only when the app there next reaches the server. The app locks after the idle time set in Settings (15 minutes unless changed), unless the device is kept unlocked. **Clear this device** in Settings signs out, deletes the app's databases, Cache Storage and sessionStorage, ends this browser's push subscription (your server keeps its record of it until it expires, but cannot reach this browser any more), closes Kasten's notifications and removes the service worker. **Sign out** ends this device's push subscription, in the browser and on your server, and closes Kasten's new-mail notifications. A subscription check that is still running finishes first, so a subscription it makes ends too, and no other check starts. Sign-out waits at most 5 seconds for this. A browser without Kasten's service worker has no subscription, so sign-out does not wait there. After 5 seconds it ends the keys and the decrypted mail anyway, and says that notifications may still arrive. It closes the notifications shown in any case. A lost device keeps getting notifications with the sender and subject until you press **Stop notifications on other devices** in Settings on another device, or for at most 7 days. Ending its sign-in alone does not stop them, because your server pushes to every subscription that has not expired. Your other devices subscribe again at their next check while unlocked.
- **Data on one device.** If the browser evicts Kasten's storage, or you clear the site's data, that device loses its key, its drafts and its unsent mail in the Outbox. The device then signs in and unlocks with a passkey or the recovery code, from the key on the server; it needs the recovery sheet only when the server has no usable copy. A key whose recovery code is lost, and whose passkeys are gone too, cannot be recovered; neither can a forgotten passphrase you chose. After `kasten lock` the only way on is then a new key, which cannot read older mail. The unsent mail is lost: the server has no copy of it.
- **New-mail notifications.** While **Show sender and subject in notifications** is on, which is the default, the app asks Stalwart to put the sender and subject of new mail into each push. The push is encrypted for your browser (RFC 8291), so your browser vendor's push service sees only when it arrives and how large it is. Your lock screen can show the sender and subject. Turn the setting off on a device to get pushes without them: that device's new-mail notifications then say only "New mail".
- **The operator key.** Whoever holds the operator's secret key can read all stored mail. An agent that reads mail sends that mail to its model provider. Never put the operator's secret key on the mail server.
- **Backups, against their key holders.** Anyone with the restic password and bucket access can restore the database. The bodies stay encrypted to your key bundle, but the metadata becomes readable.
- **Deletion.** Someone with root on the server, or with a bucket key that can delete, can destroy mail. Use the backup key choices in [operations](operations.md#backups) to delay this, not to prevent it.

## The key on the server

So that a new device needs only your sign-in and a passkey, the app keeps your key, and what opens it, in a top-level folder named **Kasten key**, which the app hides. Each message there is one OpenPGP message encrypted to a password only. Stalwart stores such a message as it is ([rule `pgp-armor-text`](#messages-the-server-stores-as-they-are)), so a device without the key can read it, and `kasten check` lists it as stored as it is. `kasten read` skips the folder, so an agent's model provider never receives it.

- **The key copy.** One message holds the recovery sheet's passphrase-protected private key, encrypted once more with the same recovery code or passphrase, with the iterated-and-salted S2K at its highest count (byte 255, about 65 MB of SHA-256 per guess).
- **The recovery code.** A key made in the app gets a recovery code instead of a passphrase you choose: 25 random base32 characters (125 bits), shown with the recovery sheet and printed on it, for you to keep in your password manager too. Nobody can guess it, so the key copy cannot be opened by guessing. The sheet then opens your key by itself: keep it like a house key. **Choose my own passphrase** keeps the older way, where the sheet needs the passphrase, and the key copy is as strong as that passphrase.
- **Passkeys.** One message per passkey holds the recovery code, encrypted to a secret that only that passkey gives this app (the WebAuthn PRF extension: the authenticator derives 32 bytes from the passkey's own secret and a fixed salt that names this purpose, after it verifies your face, fingerprint or PIN). HKDF-SHA-256 turns those bytes into the message's password. Its headers name the passkey's credential, the salt, how the passkey connects and what it is, such as "iCloud Keychain"; nothing in them opens anything. The passkey belongs to the app's own host name, so another site cannot ask it for this secret. The app adds a passkey only after it has asked it once more and got the secret, the same one when the passkey also gave it while it was made, so a provider that cannot give it, or gives a different one each time, is refused when you add it. iCloud Keychain, Google Password Manager, 1Password and YubiKeys in Chrome, Edge and Firefox give it; Safari gives it for security keys only from version 26.4, with open WebKit bugs.
- **Who can try to open them.** Someone with root on the server, anyone with the restic password and bucket access, and anyone holding a sign-in to your account can copy every message there. A passkey record opens only with that passkey and your face, fingerprint or PIN. The key copy opens with the recovery code, which cannot be guessed, or a passphrase you chose, which can be: use four or more random words. Argon2 would make each guess far more expensive, but openpgp.js runs it in WebAssembly, which the app's CSP forbids.
- **Who can replace them.** Any sign-in to your account can write mail, so it can replace the key copy or add a passkey record. A record made without your recovery code holds a code that opens nothing, and a replaced key copy does not open with your code: the new device then says so, and the recovery sheet still works. When the app can read the key settings, it also refuses a copy whose key is not in the server's key bundle.
- **Who can add a passkey.** A device that has shown you own the key in this session: you typed the recovery code or passphrase, used a passkey, or made or restored the key there. A device that unlocked by itself (**Keep unlocked on this device**) must first get a passkey you already have, or the recovery code. The same rule leaves the recovery code off a sheet printed again there.
- **Removing a passkey.** **Remove** in Settings deletes its record on the server, so new devices cannot use it. Devices that already hold the record keep it until they next connect, and backups keep it longer. The recovery code does not change, so a lost passkey opens your key wherever a copy of its record survives. To stop it for good, make a new key.
- **A passkey that changes its answer.** A browser or system update has in the past changed the secret a passkey gives (Safari 26.4 with security keys; iOS 18.0 to 18.3 across devices). The passkey then no longer opens its record, and the app says so: enter the recovery code, remove the passkey and add it again.
- **When a device writes the key copy.** Only a device whose key the server is known to encrypt to. Before `kasten lock`, the key settings show the key in the bundle. After the lock the app cannot read them, so the newest Inbox message that Stalwart encrypted must be encrypted to exactly this device's key and the operator keys, and open with the key. The proving message must also have arrived after the copy it replaces, so a key waiting for the operator, or one the operator has replaced, never qualifies. A device that made a new key writes it the next time it starts, signs in or unlocks after mail encrypted to that key has arrived; the passkey records of the former key then go. A new device on a locked account checks the mail the server encrypted after the copy was stored, and refuses the copy when that mail is encrypted to other keys, as in the time between a key change and the copy following it. A copy that names a device's key but does not open to it with that device's passphrase is written again; one the app cannot read sends a new device to the recovery sheet. A sender could forge such a message only with your public key, which Kasten does not publish.
- **What passkeys do not change.** Someone who controls the app host can still change the app and steal your key when you next unlock, whichever way you unlock.

## Messages the server stores as they are

Stalwart v1.0.1 does not encrypt every message. It stores these kinds as they arrive, under LUKS only:

- **JMAP drafts.** The app saves a draft on the server only for the few seconds of a send.
- **Mail that arrived before the account had a key bundle.** Stalwart decides whether to encrypt a message only at the moment it arrives (`crates/email/src/message/ingest.rs`, lines 610–622 at v1.0.1). Mail stored before your key was in place stays readable. `kasten check` reports each such message as a finding.
- **Messages that look already protected.** Stalwart skips any message whose top-level type is `application/pkcs7-mime` or `application/pkcs7-signature`, an `application/octet-stream` attachment named `.p7m`, `.p7s`, `.p7c` or `.p7z`, or `multipart/encrypted`. It also skips a message of at most two parts whose text starts with `-----BEGIN PGP MESSAGE-----`. This rule is in `crates/email/src/message/crypto.rs` (`is_encrypted`, lines 355–404 at v1.0.1).

The last rule has a side effect. An S/MIME message that is signed but not encrypted ("opaque-signed") is stored readable. A sender can also make their own message skip encryption by shaping it this way. `kasten check` lists each readable message of this kind as an exception, so you can see them. OpenPGP mail that is not encrypted to exactly your key set, such as mail a sender encrypted to other keys, is a finding.

After review, an operator can list a finding of this kind by its email id, in the file that `checkExceptionsFile` in `kasten.json` names. The check then reports it as an exception. A Sent copy that is not encrypted to the key set is a finding until an operator lists it, whatever its date, such as an imported one that Stalwart stores as-is. The date cannot separate an import from the app's own copy, because the app and the import source each choose a message's `receivedAt`. One exception trusts that date: after a key change, the check accepts a Sent copy that is encrypted to exactly an earlier pinned set and dated before the change, as `earlierKeySet`, like delivered mail. The sending device chose that date, so a client that dates such a copy back is excused too. Kasten accepts this. An earlier set holds only the owner's former key and the operator keys of that time. After `kasten lock`, the app cannot read the server's bundle (`x:PublicKey/get` is `forbidden`), so it encrypts each Sent copy to the key on the device and the operator keys in `/config.json`. `lock` signs every app session of the account out, but a device that still holds the former key keeps encrypting Sent copies to the earlier set after it signs in again. With a correct clock, those copies are dated after the change and are findings. A copy from a device whose clock is behind, or a message that the device queued before the change, is excused. Clear every other device after a key change. A draft stays a finding, even when it is listed.

## Plaintext residue, and why LUKS is required

Message encryption is not disk encryption. A test on Stalwart v1.0.1 with SQLite found readable message bodies on disk after Stalwart had encrypted and cleaned up:

- the SMTP queue copy of each incoming message, until the hourly blob cleanup;
- SQLite write-ahead-log pages, until the next data cleanup;
- free pages and unused space inside the database file, which can last indefinitely;
- JMAP uploads, until their upload lifetime ends (5 minutes in Kasten).

Stalwart has no setting that wipes these. Kasten therefore requires the whole data directory on LUKS, with restic's temporary files on the same disk. The nightly backup is an SQL dump of the live database (`sqlite3 .dump`), so it holds none of this residue.

The server refuses to start Stalwart unless the data directory holds the marker that `kasten-server init` wrote, with the volume id that `KASTEN_VOLUME_ID` names. A failed unlock therefore never creates an empty mailbox.

## Automatic unlock

Without a Tang server, you unlock the disk over SSH with a passphrase after each reboot. With Tang on a second machine, the disk unlocks itself when the VPS can reach Tang.

Tang adds no protection against these attackers:

- someone who clones the running VPS, together with its network identity;
- the hosting provider, or anyone with your provider panel login, because a snapshot or a rescue boot can reach Tang as the VPS;
- someone who controls both the VPS and the Tang machine.

To reduce the panel risk, turn on TOTP for the provider login, restrict access to the server control panel, and take no snapshots. The one exception is an optional snapshot during [the Fedora release upgrade](operations.md#the-fedora-release-upgrade), which the owner approves and which is deleted once the upgrade's checks pass. [The install guide](install-vps.md) has the steps.

## The browser boundary

The app runs on a host that is separate from the mail server. A break-in on the mail server alone therefore cannot replace the code that handles your key. This holds only while the mail server holds no credential for the app host or the app name: no deploy key, no CI token, no DNS token and no password manager access.

The boundary protects your key and your encrypted archive. It does not protect new mail or readable residue on the mail server. It is weaker than a signed native app, because you trust the app host and its release process every time you open the app.

The app also limits what hostile mail and a stolen session can do:

- **Message HTML.** DOMPurify sanitises it with the message frame's own window. The frame is one of two static pages on the app's own origin, `/frame/message.html` and `/frame/message-remote.html`. Each has its own Content Security Policy that allows no scripts, and the iframe sandbox never has `allow-scripts`. [web/README.md](../web/README.md#message-frames) has the details.
- **Remote content.** Nothing remote loads before you press **Show** for a message. After **Show**, only images load, and only over `https`. The sanitiser always removes `srcset`, and remote styles, fonts and media never load.
- **The app's own policy.** Its Content Security Policy allows scripts, styles and workers only from the app's origin, and connections only to that origin and the mail API.
- **Your account password.** You type it, and your sign-in codes, only on Kasten's sign-in page, which the mail server serves at `/signin/` from its own image. The app host never sees them, which matters because your password can still change your key set after `kasten lock`. The page's policy allows scripts only from the mail server, and the server forbids framing it (`X-Frame-Options: DENY`).
- **Key and MFA changes.** `kasten lock` makes the app's OAuth client non-first-party and destroys the client's grants in the account it locks. A new app token can still read and send mail, but gets `forbidden` on every `x:*` object: the key set, MFA, app passwords and account settings. Lock proves this with a new sign-in as the probe account, whose token must get `forbidden` on `x:PublicKey/set`, `x:AccountSettings/set` and `x:AppPassword/set`. The client is shared, so every new sign-in, in every account, gets the restricted rights. Lock destroys grants only in the account it locks, so run it for every account: until then, an existing sign-in of another account may keep its first-party rights. Lock refuses an account without sign-in codes, because without them the password alone can still change the key set over HTTP Basic. `--no-mfa` overrides that. After the lock, the app cannot change sign-in codes: `kasten user mfa new` and `kasten user mfa enrol` turn them on, with an authenticator key that the operator generates, and `kasten user mfa reset` turns them off.

Until `kasten lock` runs, an app token has the account's full rights. A stolen session in that window could replace your key set, and new mail would then be encrypted to the thief's key. Lock therefore compares the bundle's user key with the fingerprint on your recovery sheet (`--user-fingerprint`) before it changes anything, so it refuses a key set that was replaced before the lock. App passwords and API keys also keep their rights after the lock, and one with `Inherit` rights can still change the key set. Lock therefore pins nothing while the account has an app password or API key that Kasten did not create. `--revoke-others` destroys them, with readback.

After the lock, `kasten check` compares the live key set with the pinned one every day and reports a change. The app shows a change too: a device whose key is no longer in the server's key set opens **Restore your mail key** instead of your mail. When the operator changes the key set and runs `kasten lock` again, the check still accepts mail encrypted to the old set, but only mail that arrived before the server took the new bundle.

Lock counts an app password as Kasten's own, and keeps it, when it has the description of Kasten's reader or import password and a permission list inside that purpose's list, whoever created it. Such a credential cannot change keys or send mail. It can read stored mail, and an import one can also add messages and folders, copy messages and change flags over IMAP.

## The SMTP boundary

Kasten does not make ordinary email end-to-end encrypted. Gmail, Outlook and every other sender see the mail they send you. SES sees the mail you send. True end-to-end protection needs senders and recipients who encrypt on their own side.

The server never sends mail from its own IP. Its firewall blocks outgoing port 25. It sends only through SES on port 587, with `STARTTLS` required and the certificate verified.

## Admin access

- The Stalwart web admin UI is off. Bootstrap stores it disabled, so `/admin/`, `/account/` and `/` answer 404.
- Management uses one admin API key, for a key-only admin account. The key works only from the addresses in `admin.allowedIps`. In production these are the VPS's own loopback addresses, `127.0.0.1` and `::1`. You reach the admin listener on `127.0.0.1:8080` from the VPS itself, through `kasten-cli`. From your computer, an SSH tunnel over Tailscale should also work, for example `ssh -N -L 8080:127.0.0.1:8080 root@<vps-tailscale-name>`, because Stalwart then sees `127.0.0.1`. That route is not yet tested. From any other address, the key gets HTTP 403. `kasten security-check` proves that the key is refused from the address it runs on.
- Mail credentials have no admin rights. A user's password, an app password with `Inherit` permissions and an OAuth token all get `forbidden` on server objects such as `x:Domain` and `x:Account`.
- Public OAuth client registration, device sign-in and Stalwart's built-in `/login` page are refused through Stalwart's `allowedEndpoints` rule. That rule fails open on a wrongly typed expression, and it does not apply to loopback clients. `kasten security-check` therefore tests the refusal with live requests from a non-loopback address.
- CORS names only the app's origin. Stalwart's CORS headers are static, so every response carries `Access-Control-Allow-Origin` with the app's origin, whichever site asked. Browsers compare that header with their own origin, so other sites cannot read the responses. `kasten security-check` fails if the header is `*` or echoes the caller's origin.
- The recovery admin login works only during the first-boot bootstrap. Only `kasten-server recovery` sets `STALWART_RECOVERY_ADMIN`, and `kasten-bootstrap` runs it in a container without any network. `kasten-server serve` refuses to start while any `STALWART_RECOVERY_*` variable is set. The login file stays on the encrypted volume. `kasten security-check --recovery-admin-file <file>` proves that it no longer signs in.

## Container isolation on the host

Every container on the mail server runs under rootless Podman as the host user `kasten` (uid and gid 2600). Nobody logs in as `kasten`: it has no password and no login shell. Root runs Podman as `kasten` through `kasten-podman`. No container runs as host root.

| Setting           | The mail containers                                                                                                                 | The CLI containers                                                                                                                         |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Which             | `kasten-mail`, `kasten-recovery` and each `kasten-mail-run`                                                                         | Each `kasten-cli` run, and the CLI that `kasten-bootstrap` runs                                                                            |
| Host user         | `KASTEN_MAIL_UID`, a subordinate ID of `kasten` (the image's uid 2525)                                                              | `kasten` itself (container root)                                                                                                           |
| Capabilities      | All dropped except `NET_BIND_SERVICE`, which Stalwart's binary needs to start. It counts only in the container's own user namespace | None                                                                                                                                       |
| Other limits      | No new privileges, a read-only root file system, 768 MiB of memory                                                                  | No new privileges, a read-only root file system, 384 MiB of memory, and an init process (`--init`), so a stop or a lock ends a running CLI |
| SELinux MCS level | `s0:c525,c526`                                                                                                                      | `s0:c600,c601`                                                                                                                             |
| Writes to         | `/var/lib/kasten/data` on the volume, and a 4 MiB tmpfs                                                                             | `/var/lib/kasten/cli/state` on the volume (the bootstrap CLI: all of `/var/lib/kasten/cli`), and a 16 MiB tmpfs                            |

Two layers keep the mail server away from the CLI's credentials, such as the admin API key:

- **File ownership.** The mail server runs as `KASTEN_MAIL_UID`. The CLI's files belong to `kasten`, without group or other access, and no mail container mounts them. `kasten-cli` refuses to run while any file in `/var/lib/kasten/cli` is not `kasten:kasten` or allows group or other access.
- **SELinux MCS.** File ownership alone is not enough. Rootless Podman maps container root to the host user `kasten`, so a process that became root inside the mail container would be the owner of the CLI's files. Each class of container therefore runs at a fixed MCS level, and `:Z` on every bind mount labels the mounted directory with that level. A process at the mail level cannot read a file at the CLI level.

The levels are fixed on purpose. With Podman's random levels, each new container would relabel the data directory with its own level, and the running mail server would lose access to its own data.

Enforcing SELinux is required:

- `install.sh` refuses to run unless SELinux enforces the targeted policy with MCS. `kasten-podman` refuses to create a container unless `getenforce` prints `Enforcing`.
- The file `/etc/kasten/test-without-selinux` lifts both checks for the local container test, which cannot enforce SELinux. Both then print a loud warning and write `event=selinux-check result=skipped` to the journal. Never create this file on a real host: without SELinux, the mail server could read the CLI's credentials.
- One container-related SELinux denial is known. Once for each user, at that user's first `podman info` (for `kasten`, install.sh's), Podman runs pasta to read its version, and SELinux refuses pasta (`pasta_t`) `{ read write }` on a `container_runtime_t` `unix_dgram_socket` that it inherits from Podman. No container is involved, and the policy does not audit this denial: only with the dontaudit rules off is it logged. The Lima stages count it apart (`KNOWN_AVC` in `deploy/test/lima/lib.sh`) and fail on any other container-related denial, except the one that the MCS check of `f45` provokes on purpose.

Other host settings, and their limits:

- **Container state in RAM.** Podman's transient store keeps its database and each container's state in `/run/user/2600/containers`, in RAM. That state includes the environment of every exec, such as the backup settings, and the arguments of every run, such as an address in a CLI command. The images stay on the root disk, in `/home/kasten/.local/share/containers/storage`.
- **Backup settings in a process's arguments.** `kasten-podman` hands `RESTIC_REPOSITORY`, `RESTIC_PASSWORD_FILE` and `KASTEN_BACKUP_ENV_FILE` to Podman as `env -i NAME=value … setpriv … podman`. For the instant before `env` runs `setpriv`, their values are in `env`'s argument list, and every user on the host can read a process's arguments in `/proc/<pid>/cmdline`. No copy reaches the journal or the disk. Keep credentials out of `RESTIC_REPOSITORY`, and put them in the file that `KASTEN_BACKUP_ENV_FILE` names.
- **No core dumps.** A core dump holds the crashed process's memory, with decrypted mail and credentials. Fedora's systemd-coredump would store it on the unencrypted disk. Kasten stores none; the journal in RAM records only the crash.
- **auditd is masked.** It would write the audit log to `/var/log/audit/audit.log` on the unencrypted disk. The kernel's audit messages, SELinux denials included, still reach the journal in RAM, but the next reboot clears them. After a break-in, less forensic data is therefore left.
- **systemd-oomd is masked.** Under memory pressure it kills every process in a cgroup, and the cgroup it picks could be the one that holds the mail server. The containers' memory limits and the kernel's OOM killer stay.
- **Port 25 without root.** The mail server binds ports 25 and 443 as an unprivileged user. `/etc/sysctl.d/50-kasten.conf` therefore lets unprivileged processes bind ports from 25 up, for IPv4 and IPv6. Ports below 25, such as SSH on 22, stay privileged. While the mail server is stopped, any process on the host could bind port 25 or 443.
- **Mount propagation.** The containers see the volume because systemd mounts `/` as shared: the mount at unlock reaches Podman's mount namespace, and the unmount at a lock removes it there too. If a provider's tool made `/` private, Podman would not find the data directory and would refuse to start the mail server, so mail fails closed.
- **`/sys`.** A rootless container on the host network sees the host's `/sys` pseudo-files as read-write. Their ownership, by IDs outside the container's user namespace, and SELinux's `container_t` type should block writes. The Lima VM showed only the mounts; no write was tried.
- **Root and the containers' directories.** `/home/kasten` and `/var/lib/kasten/cli` belong to `kasten`, and `/var/lib/kasten/data` to `KASTEN_MAIL_UID`. A process that runs as either user, a container's root included, can leave a link there. If root wrote, chowned or chmodded a path through such a link, that user would gain any file on the host, and with it root. So root does not: `install.sh` creates `kasten`'s Podman settings and `cli/state` as `kasten`, `kasten-bootstrap` reads the recovery login as the mail server's user and writes its copy as `kasten`, and the operator writes files there as the directory's owner, with `setpriv`, as in [How to run the commands](operations.md#how-to-run-the-commands-on-this-page). A link then leads only to what that owner could change anyway. The root-owned parts stay root's: `/var/lib/kasten` itself, the volume's `secrets/` and the files in `/etc`.
- **The provider's metadata service.** The firewall lets root alone reach `169.254.169.254` and `fe80::a9fe:a9fe` on TCP port 80, for cloud-init on Hetzner. A container's user cannot reach it.
- **The fixed uid 2600.** The units and `kasten-podman` name the `kasten` user by number. If uid or gid 2600 already belongs to someone else, as could happen on a provider's image, `install.sh` stops at its `user` step. It also stops if the subordinate ID range of `kasten` changes, because the mail files belong to `KASTEN_MAIL_UID`.

## Logs, downloads and backups

- **Logs.** Every container logs to journald, which keeps logs in RAM only (32 MiB), so they do not survive a reboot. Stalwart logs at `info`: envelope addresses, client IP addresses, account names and Message-IDs, but no subjects or bodies ([details](stalwart-v1.0.1.md#14-logging)). Podman writes no log file to the disk: its only one, the health-check log, is in `/run/user/2600`, in RAM. Before `install.sh`, the Fedora Cloud image keeps a persistent journal in `/var/log/journal`, and auditd writes `/var/log/audit/audit.log`. Those files from before `install.sh` stay on the disk. They hold only the logs of the first boot and of the install. `/var/log/dnf5.log` also stays on the disk; it holds package names only.
- **No runtime downloads.** Stalwart's first start runs without any network, through `kasten-bootstrap`. Bootstrap stores the web admin UI, ASN/GeoIP data and the spam rules' four remote lists (OpenPhish, PhishTank, disposable and free mail domains) as disabled. The spam rules come from a pinned local file. DNS blocklist lookups stay on; they are DNS queries through the server's own resolver, not downloads.
- **Automatic updates.** `dnf5-automatic.timer` downloads and applies all Fedora updates every morning, unattended: security and bug fixes, and also new upstream versions of Podman, crun, systemd and the kernel. It never reboots; `dnf5 needs-restarting` says when a reboot is due. A running container keeps the old Podman and crun until its next start, and a new kernel or systemd takes effect at the next reboot. dnf5 fetches only from HTTPS mirrors, because the firewall closes outgoing port 80. The risk is that a behaviour change in Podman, crun or systemd lands with nobody watching. The daily check and the delivery probe show its effect, not its cause.
- **Backups.** restic encrypts each snapshot with the restic password before it leaves the server. The password lives on the encrypted volume and in your password manager. A snapshot holds the whole database: the bodies encrypted to your key bundle, and the metadata and the messages stored as they are in readable form.
- **The operator key.** You keep the operator's secret key and its passphrase in your password manager. The mail server and the app host hold only its public key. An agent gets the secret key only to read mail, on your computer, through a pipe or, when no pipe is possible, as `0600` files ([agent setup](agent-setup.md#reading-mail)).

## When to stop and decide

Stop before real mail or the MX switch if any of these happens. Do not work around it with another provider, a helper service or a weaker setting. Read the evidence and choose the next step yourself.

| Failure                                                                          | Why it matters                                                                                                             |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| SES refuses production access                                                    | You cannot send                                                                                                            |
| Inbound port 25 does not reach the VPS                                           | You cannot receive                                                                                                         |
| The real server fails the memory or speed acceptance                             | Mail can be refused or lost under load                                                                                     |
| Automatic unlock through Tang fails its acceptance                               | Mail waits after every reboot until someone unlocks the disk                                                               |
| `kasten security-check` fails: registration or management calls are not refused  | Strangers could register clients or manage the server                                                                      |
| The exact-origin CORS preflight fails                                            | The docs must then not claim that CORS restricts which sites call the API                                                  |
| `kasten lock` cannot remove the app's account-settings permission                | A stolen session can still replace your key set after the lock. The fingerprint check covers only the time before the lock |
| `kasten lock` refuses because the user key is not the one on your recovery sheet | Someone may have replaced your key set before the lock                                                                     |
| The user MFA API is missing on the pinned release                                | You cannot protect the mail login with a second factor                                                                     |
| A readable Sent copy remains after a send                                        | Sent mail is stored readable                                                                                               |
| Push, decryption, storage or search fails on your real phone                     | The app does not meet its purpose on that device                                                                           |
| `kasten check` reports a key set you did not set                                 | Someone may have replaced your key                                                                                         |

## Reporting a problem

Kasten is pre-release. Report a suspected vulnerability privately to the repository owner, not in a public issue.
