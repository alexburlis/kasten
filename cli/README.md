# kasten (CLI)

The `kasten` command configures Stalwart through its admin API, prints DNS records, manages accounts, key bundles and app passwords, locks the app's OAuth client, runs the daily safety check and delivery probe, reads mail for an agent, and imports old mail over IMAP. It is TypeScript that Node 24 runs directly (type stripping). Its only dependency is `@kasten/core`, so it runs the same crypto, MIME, JMAP and safety code as the web app.

## Run it

| Where                      | Command                                                                                                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A checkout, with Node 24   | `node cli/src/main.ts <command>` from the repository root, after `pnpm install`                                                                                                                                          |
| The local dev stack        | `./kasten <command>` from the repository root, after `./kasten dev up`. It runs the `kasten-cli:dev` image and adds `--config /kasten-dev/kasten.json` to the commands that take one ([dev/README.md](../dev/README.md)) |
| The production VPS         | `kasten-cli <command> --config /etc/kasten/kasten.json`, as root, from any directory. Piped standard input works as it is                                                                                                |
| Any machine with the image | `docker run --rm kasten-cli:<tag> help` ([The image](#the-image))                                                                                                                                                        |

`./kasten` mounts `.kasten-dev/` read-only at `/kasten-dev`, which is also the working directory. Only `/kasten-dev/state` and `/kasten-dev/out` are writable, so give container paths such as `--out /kasten-dev/out`.

On the VPS, `kasten-cli` runs the image once, in a new, temporary container on the host network, so it reaches the admin API on `127.0.0.1:8080`. It sees `/var/lib/kasten/cli` read-only as `/etc/kasten`. Only `/etc/kasten/state` (the default `stateDir`) and `/tmp` (16 MiB in RAM) are writable. It runs as uid 0 without capabilities, and rootless Podman maps that uid to the host user `kasten`. So every file and directory in `/var/lib/kasten/cli` must belong to `kasten:kasten`, without group or other access. Otherwise `kasten-cli` refuses with exit status 2 and prints the fix: `chown -R kasten:kasten /var/lib/kasten/cli && chmod -R go= /var/lib/kasten/cli`.

Secrets come only from files or standard input, never from arguments. A secret file holds the secret on its first line. A regular file or a named pipe must give group and others no access (`chmod 600`), or the command stops. A secret file can also be an unnamed pipe or socket, such as `/dev/stdin` from a shell pipe or `/dev/fd/N` from `<(command)`; the CLI reads it without a mode check. A file redirected to `/dev/stdin` (`< file`) is checked like the file itself. The CLI refuses anything else, such as a directory or a device. Output never contains a secret. Setup prints property names, not values.

### Exit codes

| Command          | 0                                          | 1                                                                       | 2                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------- | ------------------------------------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`          | Clean (every checked account)              | Findings                                                                | An error, pushed as `down`: an unreadable or invalid kasten.json (pushed when it still names a readable `kumaPushUrlFile`), an unreadable admin API key file, an account that cannot be checked, or a Kuma push that fails or is refused. Also a usage error                                                                                                                                                                                            |
| `probe`          | Today's message arrived                    | Not arrived (yet), refused, or the outcome uncertain                    | An error, pushed as `down` when the probe's push URL file can be read: an unreadable or invalid kasten.json, one without `probe`, an error during the probe, or a Kuma push that fails or is refused. | `import-imap`    | Every source message is in the destination | Not clean, or an error                                                  | A usage error, including a `--folder` that names a folder the source lacks, cannot select or holds as a virtual folder                                                                                                                                                                                                                                                                                                                                  |

## kasten check

`kasten check` is the daily safety check. It needs the pin from `kasten lock`, the admin key (to read the live bundle) and the reader credential from `kasten reader create`. With `--account` it checks that account. Without it, it checks every account in `users` except the probe account, one after the other, so each of them needs its pin and reader. Then it pushes one combined result to Kuma.

1. It compares the live key bundle with the pin: the same key fingerprints, no expiry and no other bundle problem, with encryption at rest on. It does not compare the encryption subkeys directly. It classifies mail against the pinned encryption subkey ids, so a subkey that changed under the same fingerprint shows up as `notEncryptedToKeySet` findings on mail that arrives after the change.
2. It lists every email with its mailbox roles, keywords and `receivedAt`, through the reader credential.
3. It classifies each stored message with `@kasten/core` (`classifyStored`, `checkMailbox`): encrypted to exactly the pinned subkeys, a listed exception, or a finding. Findings are `keySetMismatch`, `keyExpiry`, `bundleProblem`, `notEncryptedToKeySet`, `plaintextSent` and `staleDraft` (a readable draft older than one hour). Exceptions are `stalwartStoresAsIs`, `freshDraft`, `listed` (an email id in `--exceptions`, or, when the run names no file, in kasten.json's `checkExceptionsFile`) and `earlierKeySet`: a message encrypted to exactly a key set that a later `kasten lock` replaced, which arrived (`receivedAt`) before Stalwart took the new bundle (`replacedAt` in `lock.json`). A message encrypted to that set that arrived in that second or later is a `notEncryptedToKeySet` finding, so new mail must use the current set. A listed id never excuses a draft, which follows the draft rule. A Sent copy that is not encrypted to the key set is `plaintextSent` or `notEncryptedToKeySet` until it is `listed`, whatever its date, such as an imported one that Stalwart stores as-is: the app and the import source each choose a message's `receivedAt`, so the date cannot tell an import from the app's own copy. The one exception is `earlierKeySet`: it also accepts a Sent copy encrypted to exactly an earlier set, by the date that the sending device chose. `docs/security.md` says why Kasten accepts that.
4. It is incremental. `Email/changes` gives the new and changed messages since the last run, and only those are downloaded. A download stops after the first 16 KiB when that shows the structure and the PKESK packets, and reads at most 64 KiB before it falls back to the whole message. `--full` rescans everything; so does every run 7 days after the last full scan.
5. It prints a report without correspondents' addresses or subjects (it names only the checked account), and pushes the result to `kumaPushUrlFile` unless `--no-push`: `up` with `clean: <n> messages, <n> exceptions`, or `down` with the finding kinds and counts, or `check error, see the log`. A run over several accounts adds the number of accounts, for example `clean: 2 accounts, 7 messages, 1 exceptions`, or `check error for 1 of 2 accounts, see the log; 2 findings: plaintextSent 2; 2 accounts, 7 messages`. The exit status is the worst of the accounts: 0 clean, 1 findings, 2 error.

```text
scan      incremental: 3 new or changed, 0 removed
read      3 messages: 3 from their first bytes, 0 whole, 12 KiB in total
result    you@example.com: 5 messages, 2 encrypted to exactly the key set, 1 exceptions, 2 findings
exceptions freshDraft 1
FINDING   plaintextSent <email id>: <reason>
FINDING   staleDraft <email id>: <reason>
pushed    Kuma: down, "2 findings: plaintextSent 1, staleDraft 1; 5 messages"
```

## kasten probe

The probe account (`config.probe`) sends one message a day to itself. Setup's route rule sends that message out through the relay (SES), so it comes back in through the public MX. The probe follows it: `relay accepted` when the submission's delivery status says the relay took it, then `received` when it is in a mailbox. It deletes the received copy, records the times in `<stateDir>/probe.json` and pushes to `probe.kumaPushUrlFile`: `up` with `received: relay <s>s, mailbox <s>s (<mailbox role>)`, otherwise `down`.

- The Message-ID is `kasten-probe-<YYYYMMDD>@<domain>`, one per UTC day. SES replaces the Message-ID, so the probe knows the copy that comes back by a random marker in its subject, which `probe.json` keeps from before the submit.
- While `probe.account` stays the same, the probe sends at most once per UTC day. A run that finds today's message `received`, `failed` or `uncertain` only reports it. A run that stopped during the submit leaves `submitting`, which the next run reports as `uncertain` and never resends.
- After `probe.account` changes, the next run sends and proves the new account, even on the same day. The earlier account's result never counts for it, and an earlier uncertain or failed result does not block it. `probe.json` keeps only the latest account's attempt, so switching back to an earlier account on the same day sends again. A `probe.json` from before the account was recorded counts for any account in the domain that its Message-ID names.
- Setup forbids relaying for the probe account, so it cannot send to other domains (the submission's delivery status says `550 5.7.1 Relay not allowed.`). Stalwart v1.0.1 cannot limit it to its own address, so it can still send to local addresses. See [docs/stalwart-v1.0.1.md](../docs/stalwart-v1.0.1.md#15-the-probe-account-and-its-route).
- The personal deployment runs the timer independently on apps, using the pilot account during the pilot and switching accounts/state at final MX. The generic co-located VPS timer is installed but never enabled by install.sh; see [observer setup](../deploy/observer/README.md).

## kasten import-imap

For content reconciliation against encrypted destination mail, supply protected local `--key <operator-secret.asc> --passphrase-file <file>` (repeat `--key` for historical keys). An encrypted candidate that cannot be decrypted is an explicit error, never a header-only match. Keys stay on the importing computer. Matching uses content and preserves same-folder duplicate multiplicity. Label folders, and any message in several real folders, share one destination Email through IMAP COPY. Virtual folders (RFC 6154 `\All` such as All Mail, `\Flagged` such as Starred) are never copied as folders. After the real folders finish, the import matches each message of a virtual folder to a message that another folder holds: by Message-ID, header fingerprint and size, and by SHA-256 of the source bytes when the Message-ID is missing or shared. Each held message matches one message of the virtual folder; another message with the same bytes is a separate message and gets its own Email, not a membership of the held one. A message that no folder holds is copied into a folder with the virtual folder's name, and the report names it in a `Note`.

```text
kasten import-imap --source-host <host> --source-port <port> [--source-tls implicit|starttls|none]
    [--source-ca <file>] --source-user <user> --source-password-file <file>
    --dest-host <host> --dest-port <port> --dest-user <email> --dest-password-file <file>
    --state <file> [--folder <name>]... [--dry-run]
    [--key <file>... --passphrase-file <file>]
```

It copies every selectable real folder of the source into the destination account through Kasten's IMAP import listener (`imapImportBind`), and keeps folders, keywords and internal dates. Flags follow the source both ways. A rerun removes the flags that the source dropped since the last run (`UID STORE -FLAGS`, which `imapStore` covers). Flags set only in the destination stay. Kasten keeps one set of flags per message, shared by every folder that holds it, so when the source has the same message in two folders, a flag that one of them still has stays. The import knows the same message by the SHA-256 of its source bytes, so this holds also after a rerun from a new state file, and a separate message with the same bytes keeps such a flag too. A `--folder` run does not see the folders it leaves out, so it can remove a flag that only they have; their next run adds it back. A state file from before Kasten recorded the synced flags removes no flag on its next run, which records them. INBOX goes to the Inbox and special-use folders (`\Sent`, `\Drafts`, `\Trash`, `\Junk`, `\Archive`) go to the destination's folder with the same use; other folders keep their names. When the destination has no folder with that use (Stalwart's defaults have no `\Archive`), the import creates a folder with the source folder's name and the use (`CREATE "<name>" (USE (\Archive))`, RFC 6154 CREATE-SPECIAL-USE), so the app's Archive files into it. Only one folder gets each use. A destination without CREATE-SPECIAL-USE gets the folder without the use, and the report says so. Imported `\Trash` and `\Junk` mail stays in Deleted Items and Junk Mail, because setup turns off Stalwart's 30-day automatic expunge (`expungeTrashAfter` in `x:DataRetention`).

`--folder` copies only that source folder (repeat it for more). It cannot name a virtual folder. With `--folder`, the import checks `\All` without copying into it, and reports its messages outside the named folders as missing; it leaves `\Flagged` out. `--dry-run` changes nothing.

Stalwart encrypts each appended message only when the server's `encryptAtRest` and `encryptOnAppend` and the account's `encryptOnAppend` are on and the account has a key; otherwise it stores the message in plaintext, and never encrypts it later. `kasten app-password create --purpose import` therefore refuses an account until `kasten lock` has pinned its key set and all of these hold.

- **Credentials.** `--dest-password-file` holds an app password, because an account with MFA cannot log in with its own password. Create it with `kasten app-password create --account <email> --out <file> --purpose import --config <file>`. The account must be locked first (`kasten lock`). Its `Replace` list is exactly what `import-imap` does on the destination (`authenticate`, `imapAuthenticate`, `imapCapability`, `imapList`, `imapCreate`, `imapSelect`, `imapFetch`, `imapAppend`, `imapCopy`, `imapStore`), and every JMAP method call is `forbidden`. Like every credential of the account, it can still upload temporary blobs and download blobs by id, because Stalwart does not apply permissions to those routes. Stalwart answers an IMAP command outside that list with nothing: it ends the session or stops answering, and never runs the command. After `kasten lock`, the app cannot create an app password, so the CLI creates it through the admin key. Delete it after the import with `kasten app-password delete --account <email> --id <id> --config <file>`; `tests/integration/cli-import-imap.test.ts` does both.
- **TLS.** `--source-tls` defaults to `implicit`. Certificates are always checked; `--source-ca` adds a CA. Plain IMAP is allowed only to loopback and private addresses.
- **Where to run it.** `imapImportBind` is off by default. Set it, for example to `127.0.0.1:143`, run `setup`, and restart Stalwart when setup asks. The listener has no TLS. The VPS firewall blocks outgoing IMAP ports such as 993, so run the import on your computer and forward the listener over SSH, for example `ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:11143:127.0.0.1:143 root@<vps>` with `--dest-host 127.0.0.1 --dest-port 11143`. Avoid local port 1143, which is Proton Bridge's default IMAP port. `ExitOnForwardFailure=yes` makes `ssh` stop when the local port is taken. Set `imapImportBind` back to `null` afterwards. This path has not yet been tested on a real VPS; the tests import into the dev stack.
- **Reconciliation.** Each source message is identified by folder, UIDVALIDITY and UID, and mapped to the UID the destination's `APPENDUID` returned. The state file also keeps the source size and the SHA-256 of the source bytes. Because the destination encrypts, its copy is checked by Message-ID, a fingerprint of the Date, From, To and Subject fields (Stalwart keeps them readable), internal date and flags. A message without a Message-ID is matched by the fingerprint plus the internal date. Two different messages with one Message-ID, such as a list copy and a direct copy, are both copied. Listings follow RFC 9738 `MESSAGELIMIT`, so a server that answers a large folder in parts loses nothing. A date before 1970 becomes 1 January 1970, the earliest date Stalwart stores, with a note in the report. A copy you delete in Kasten after an earlier run is listed under Skipped and not copied again. A run whose source has an `\All` folder is clean only when every `\All` message is held by a copied folder or was copied into the `\All` folder. A virtual folder is not reconciled while another folder is unfinished.
- **No duplicates.** Before each APPEND, an intent goes to the state file. A run that stopped mid-copy looks for the copy before it appends again. A run without a state file (or with `--dry-run`) still finds the copies that are there. When the destination refuses a message's keywords (Stalwart limits their number and length), the message keeps its system flags and the report says so. A state file belongs to one source and destination (host, port and user); another pair needs another file.
- **Moves and deletions** in the source are reported, not mirrored: the import never deletes or moves destination mail. When a message left a source folder after an earlier copy (moved, deleted, or the folder renumbered), the destination keeps that copy. The report lists it under `No longer in the source folder (the destination keeps the earlier copy)`, with the folders the source has it in now, and a clean result line counts these copies. A message moved to another folder gets that folder's membership through `UID COPY`, so the Email exists once. A message that returns to a folder under a new UID matches its earlier copy. Remove a listed copy from the destination folder if the move or deletion was intended; the next run no longer lists it.
- **Rate limits.** A busy or rate-limited answer (`[THROTTLED]`, `[UNAVAILABLE]`, `[INUSE]`, a `[LIMIT]` that says so, or `BYE`) or a dropped connection waits and tries again, up to 8 times, following "retry in N seconds" when the server says it. Any other `NO` to one message's `FETCH` is not retried; that message is reported refused and the folder goes on.
- **Report.** A table per folder: Source, Copied, Present, Skipped, Duplicates and Missing, then the reasons under `Skipped, no mail lost`, `Refused (not copied)`, `Missing` and `No longer in the source folder (the destination keeps the earlier copy)`. The Skipped column counts skipped and refused messages. The `Refused (not copied)` list holds messages the destination refused, messages the source refused to send (a tagged `NO` to their `FETCH` that a retry cannot help, such as a server that cannot build one message), and messages whose internal date this client cannot read. Each reason names the side: `the destination refused it: ...` or `the source refused to send it: ...`. A source refusal skips only that message: the import copies and verifies the rest of the folder, and the next run asks for the message again. An interrupted copy of a refused message stays pending until the source sends it. An All Mail or Starred message that cannot be compared, because the source refuses it or its copy in another folder, is listed as refused instead of being copied. `Result: clean.` requires zero missing and zero refused messages and no unfinished folder, so it stays unreachable while any message is refused. The listed copies that are no longer in their source folder do not make a run unclean, but review them.

```text
Reconciliation
Folder                  Source  Copied  Present  Skipped  Duplicates  Missing
Sent -> Sent Items           1       1        0        0           0        0
Entwürfe/Ärger               1       1        0        0           0        0
INBOX                        3       3        0        0           0        0
Total                        5       5        0        0           0        0

```

## First boot

1. `kasten-server init` prepares the data volume and the recovery login file. It prints the `volumeId`. Every later `kasten-server` command needs it in `KASTEN_VOLUME_ID`.
2. Start Stalwart in recovery mode (`kasten-server recovery`) **without a network**, for example with `docker run --network none`. Stalwart's very first start tries to fetch its web UI from GitHub; without a network nothing is downloaded. Run the CLI in the same network namespace, so it reaches the recovery port on `127.0.0.1`.
3. `kasten setup --config kasten.json --bootstrap --recovery-admin-file <recovery-admin file>`.
4. Stop recovery mode. Start Stalwart normally (`kasten-server serve`), with `STALWART_PUBLIC_URL` set.
5. `kasten setup --config kasten.json`. It applies the settings Stalwart creates defaults for on its first normal start (Web Push key, routes, throttles, and the spam rules' remote lists, which it disables), and checks that the session offers Web Push. In production mode it also creates the ACME provider and the certificates, which contacts the CA.
6. Run it again whenever you like: it reports `0 changed`.

`./kasten dev up` runs steps 1 to 5 for the dev stack. On the VPS, `kasten-bootstrap` runs steps 2 and 3 with Podman (recovery mode with `--network=none`, and the CLI in that container's network namespace) and stops recovery mode; [deploy/README.md](../deploy/README.md#order-of-use) gives the whole order.

Why the order matters, and every value setup writes: [docs/stalwart-v1.0.1.md](../docs/stalwart-v1.0.1.md#what-kasten-setup-writes).

Every normal setup run (without `--bootstrap`) runs `ReloadSettings`, even when it changed nothing, so settings that an earlier failed run stored become live. Setup prints `Restart Stalwart to apply: ...` when it changed listeners, applications or cleanup schedules after the first start. The hint also lists such restart-only changes from an earlier run that failed before it could print the hint. Setup keeps them in `<stateDir>/setup-restart.json` and empties that file after a successful run prints the hint.

Setup never changes the OAuth client's `firstParty` flag after creating it; `kasten lock` owns that. When `<stateDir>/lock.json` pins any account, or the server holds an OAuth client with `firstParty: false`, a client that setup must create (a new `webApp.oauthClientId`, or one that is gone) gets `firstParty: false`. So a run from a state directory without `lock.json`, such as through an SSH tunnel, keeps the lock. Before any change, setup records that client in `<stateDir>/setup-lock-due.json`. A successful run then says to run `kasten lock` for every account and empties that file, also when an earlier run created the client and failed before it could say so. Setup cannot see a lock when `lock.json` is missing and the locked client is gone.

| Use        | Build                                                                                                                        | Tag                                                                                                                                                                       |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dev stack  | `./kasten dev up` builds it from `compose.yaml` (service `cli`)                                                              | `kasten-cli:dev`                                                                                                                                                          |
| Production | `docker build --platform linux/amd64 -f cli/Dockerfile -t kasten-cli:<version> .` on your computer, from the repository root | `kasten-cli:<version>`: the same `<version>` as `kasten-server`, and `KASTEN_VERSION` in `/opt/kasten/.env`. On the VPS, Podman names it `localhost/kasten-cli:<version>` |

Copy the production images to the VPS with `docker save kasten-server:<version> kasten-cli:<version> | ssh root@<vps> kasten-podman load` ([deploy/README.md](../deploy/README.md#order-of-use)). Docker builds and saves the images on your computer. Rootless Podman loads them on the VPS and names them `localhost/kasten-server:<version>` and `localhost/kasten-cli:<version>`. The VPS never pulls images: every container starts with `--pull=never`.

The image is `node:24-slim` pinned by digest. Its entry point is `kasten`, its default command is `help`, and its working directory is `/work`. It runs as the unprivileged `node` user unless you choose another. With plain `docker run`, pass `--user "$(id -u):$(id -g)"` and mount the config directory, so the 0600 secret files are readable: `docker run --rm --user "$(id -u):$(id -g)" -v "$PWD/config:/config" kasten-cli:<tag> setup --config /config/kasten.json`.
